# Операция {{operation}}: рабочий процесс от требования до прожарки

Беклог рабочего процесса: выявить требование, завести по нему задачу на GitHub, открыть ветку
изменений и запустить прожарку формирования изменений. Предмет `subject` — адрес прогона; исходная
формулировка владельца — значение `requirement`. Код и номер задачи рождает этот прогон
и дописывает во фронтматтер.

Значения операции несёт фронтматтер — второй раз они не собираются
(BKL-005; текст нормы — `backlog norms --rule BKL-005`). Задачи исполняются
по порядку.

Порядок исполнения — отметки задач, выводимый признак «выполнено ранее», стоп-знак перед
необратимой задачей — задан BKL-006 (`backlog norms --rule BKL-006`)
и BKL-007 (`backlog norms --rule BKL-007`), а его носитель —
`{{runner}}`: прочитать его перед первой задачей; здесь он
не пересказывается (BKL-008; текст нормы — `backlog norms --rule BKL-008`). Указатель носителя несёт
и фронтматтер значением `runner`: оттуда его читает проверка, отсюда — исполнитель.

## 3. Задача на GitHub

Организационные шаблоны задач лежат в репозитории `united-software-platform/.github`,
каталог `.github/ISSUE_TEMPLATE`, — это источник истины; редактируемые копии шаблонов
в проекте не создаются. Исполнитель получает шаблоны через локальный кеш
`~/.cache/wrsp/issue-templates/`: файлы шаблонов как есть — включая `config.yml` —
и метаданные JSON (репозиторий-источник, SHA последнего полученного состояния `main`,
время получения в UTC, перечень файлов). Кеш лежит вне репозитория, не коммитится
и вручную не правится.

Работа с кешом идёт по алгоритму:

- кеша нет — получить SHA `main` репозитория `united-software-platform/.github`, загрузить
  содержимое `.github/ISSUE_TEMPLATE`, проверить полноту: число файлов совпадает с перечнем
  каталога, каждый `*.md` несёт YAML-фронтматтер с `name` и `labels`, — и сохранить кеш
  с метаданными;
- кеш есть — сначала получить текущий SHA `main`; при совпадении использовать кеш; при
  изменении — загрузить каталог заново, проверить, атомарно заменить кеш и обновить метаданные;
- GitHub недоступен — использовать последний доступный кеш и сообщить владельцу его SHA
  и время получения;
- кеша нет и GitHub недоступен — остановиться до создания задачи и назвать причину.

- [ ] 3.1 Определить тип задачи: прочитать организационные шаблоны из кеша по алгоритму выше,
  выбрать шаблон, отвечающий назначению требования из задачи 2.1, и назвать выбор владельцу
  с обоснованием; `config.yml` типом задачи не считается; владелец вправе поправить выбор.
  Имя выбранного шаблона дописать во фронтматтер в `issue_type`
  - Проверка: тип назван с обоснованием из организационных шаблонов и согласован
    с владельцем; `issue_type` во фронтматтере заполнен
  - Выполнено ранее: `issue_type` заполнен подтверждённым значением — повторный выбор
    не выполняется
- [ ] 3.2 Составить черновик задачи по выбранному организационному шаблону: заполнить все
  его разделы; сведений не хватает — выяснить их у владельца до создания задачи; выдумывать
  содержимое и оставлять обязательные поля пустыми запрещено; раздел, для которого сведений
  действительно нет, закрыть явной пометкой «— (нет)» после вопроса владельцу. Заполненный
  черновик дописать во фронтматтер в `issue_draft`
  - Проверка: черновик несёт все разделы шаблона, пустых разделов нет, недостающее
    выяснено у владельца; `issue_draft` во фронтматтере заполнен
  - Выполнено ранее: `issue_draft` заполнен — черновик уже составлен, повторное заполнение
    не выполняется
- [ ] 3.3 Провести первую прожарку черновика — вызвать навык `/mattpocock-skills:grilling`,
  передав ему черновик из `issue_draft`: уточнять формулировки и границы, пока задача
  не заполнена по шаблону и готова к созданию; итог прожарки дописать во фронтматтер
  в `issue_draft`
  - Проверка: прожарка вызвана с черновиком и довела его до готовности к созданию;
    `issue_draft` несёт итог прожарки
  - Выполнено ранее: прожарка уже шла в этом прогоне — повторный запуск только по решению
    владельца
- [ ] 3.4 **Стоп-знак.** Показать владельцу итоговый состав задачи: тип `issue_type`,
  подтверждённый заголовок `task_ref`, черновик `issue_draft` по разделам шаблона,
  репозиторий `{{target}}` и будущее имя ветки из группы 4; назвать последствия прямо:
  в репозитории появится задача, видимая всем его читателям, вернуть прежнее состояние можно
  только встречным удалением, а занятый номер повторно не выдаётся. Дождаться подтверждения,
  записать его во фронтматтер в `confirmed.irreversible_step` и завести задачу на GitHub
  в репозитории `{{target}}`; флаг `--template` не используется
  `gh issue create --repo {{target}} --title "<task_ref>" --body-file <файл черновика> --label <labels из фронтматтера шаблона>`
  URL созданной задачи дописать во фронтматтер в `issue_url`
  - Проверка: подтверждение получено непосредственно перед созданием и записано
    во фронтматтер; команда исполнена после него, `issue_url` во фронтматтере заполнен
  - Выполнено ранее: `issue_url` заполнен — задача уже заведена, повторное создание
    не выполняется
- [ ] 3.5 Сверить созданную задачу
  `gh issue view <номер из issue_url> --repo {{target}}`
  - Проверка: заголовок совпадает с `task_ref`, тело повторяет черновик `issue_draft`
  - Выполнено ранее: проверка состояния — повторяется без последствий
