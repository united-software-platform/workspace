## Описание

### Назначение

Система управляет рабочим пространством (Workspace): собирает и агрегирует данные о компаниях,
проектах, командах и бизнес-кейсах, анализирует проекты и выполняет гибридный поиск по данным
пространства.

Система — внутренний инструмент владельцев и разработчиков, а не публичный продукт.

### Действующие лица

| Действующее лицо | Кто это | Что делает |
|------------------|---------|------------|
| Владелец пространства | Единственный человек, ведущий рабочее пространство | Выполняет все операции системы |
| LLM-агент | Ассистент владельца | Выполняет операции системы через инструменты (tools) от имени владельца; результат бизнес-кейса не подтверждает |

### Понятия

| Понятие | Определение |
|---------|-------------|
| Рабочее пространство (Workspace) | Совокупность компаний, проектов, команд, бизнес-кейсов и собранных о них данных |
| Владелец пространства (Workspace Owner) | Человек, который ведёт рабочее пространство; у пространства один владелец |
| Компания (Company) | Организация, которой принадлежат проекты и команды; в пространстве может быть сколько угодно компаний |
| Проект (Project) | Один git-репозиторий, зарегистрированный в рабочем пространстве по пути; принадлежит одной компании |
| Технология (Technology) | Элемент стека проекта с категорией из открытого перечня — язык, фреймворк, платформа, хранилище данных — и необязательной версией, например `php` 8.3, `symfony` 7.1, `bitrix`, `postgresql` 16 |
| Стек проекта (Project Stack) | Набор технологий проекта; определяется сборщиком автоматически и дополняется или исправляется владельцем вручную |
| Группа проектов (Project Group) | Именованный набор проектов, в том числе разных компаний, для агрегации, анализа и поиска по подмножеству |
| Команда (Team) | Состав участников, работающих над проектами; принадлежит одной компании и работает над одним или несколькими её проектами; над проектом может работать несколько команд |
| Участник (Member) | Человек, учтённый в пространстве для анализа: кто что делал и из кого состояла команда; учитывается один раз, может состоять в нескольких командах; операций в системе не выполняет |
| Членство в команде (Team Membership) | Участие человека в конкретной команде: роли участника и период — дата входа и дата выхода, обе необязательны |
| Роль участника (Member Role) | Роль человека в рамках членства в команде из открытого перечня, например `dev`, `qa`, `data engineer`, `ai engineer`, тимлид, архитектор; права доступа не задаёт |
| Бизнес-кейс (Business Case, BC) | Бизнес-решение и задача: проблема, решение и, при наличии, измеримые метрики; результат подкрепляется данными git проектов, к которым относится BC |
| Сборщик (Collector) | Источник данных о проекте: git, AST, метрики кода, стек проекта и другие подключаемые источники |
| Намерение (Intent) | Заявленная владельцем цель сбора: какие проекты и какие данные нужны |

### Границы

Входит: учёт компаний, проектов и их стека, групп, команд и участников, сбор данных по намерению, агрегация,
ведение BC, анализ проектов, BC и участия, гибридный поиск.

Не входит: работа участников в системе, аутентификация, авторизация и разграничение прав,
публичное использование, нефункциональные требования, модель данных, интерфейсы, архитектура,
анализ силами LLM, сбор по расписанию и по git-хукам.

## Возможности

| Код | Возможность | Суть |
|-----|-------------|------|
| CAP-001 | Управление пространством | Учёт проектов, их стека и групп, настройка сборщиков и исключений проекта |
| CAP-002 | Сбор данных | Сбор данных о проектах, инициированный намерением владельца |
| CAP-003 | Агрегация | Сведение собранных данных по проекту, группе, компании и пространству, в том числе во времени |
| CAP-004 | Ведение BC | Регистрация BC и подтверждение его результата данными git |
| CAP-005 | Анализ | Отчёты по проектам, BC и участию на основе собранных данных |
| CAP-006 | Гибридный поиск | Поиск по данным проектов и BC с объединённым ранжированием |
| CAP-007 | Учёт компаний и команд | Компании, команды, участники и их членство в командах как данные для анализа |

Возможности (Capability, CAP) — укрупнённые способности системы; каждая раскрывается операциями
(Operation, OP) в разделе [Операции](#операции). Инициатор каждой операции — владелец пространства
или LLM-агент от его имени.

## Ограничения и допущения

- **Ограничение:** пространство ведёт один человек — владелец. Участники в системе операций
  не выполняют: они — данные для анализа. Аутентификация, авторизация и разграничение прав
  не требуются.
- **Ограничение:** проект и команда принадлежат ровно одной компании; проект, общий для нескольких
  компаний, не поддерживается.
- **Допущение:** LLM-агент выполняет операции через инструменты (tools) от имени владельца;
  подтверждение результата BC остаётся за владельцем.
- **Допущение:** для ответа «кто что делал» участник сопоставляется с авторами в git-данных
  проектов; способ сопоставления — по имени или по дополнительным идентичностям — прорабатывается
  позднее.
- **Допущение:** судьба проектов и команд при снятии компании с учёта прорабатывается позднее.
- **Допущение:** стек проекта ведётся гибридно — сборщик определяет технологии автоматически,
  владелец правит их вручную; порядок совмещения ручных и автоматически определённых значений
  прорабатывается позднее.
- **Ограничение:** стек проекта пока не используется в фильтрах агрегации, сравнения и поиска
  и не анализируется отдельной операцией.
- **Допущение:** любой сбор данных инициирует владелец; намерение задаёт охват сбора. Форма
  намерения и способ его исполнения прорабатываются позднее.
- **Допущение:** git, AST и метрики кода — примеры источников, а не обязательный состав; набор
  сборщиков расширяем. Перечень языков для AST не фиксируется — он определяется доступными парсерами.
- **Ограничение:** детали агрегации — оси, периоды, хранение истории — не проработаны.
- **Ограничение:** содержание BC проработано только верхнеуровнево: состав полей, жизненный цикл
  и порядок подтверждения результата уточняются отдельно.
- **Риск:** понятие «Кейс (Case)» уже определено в [правилах документов проекта](../rules/project-docs-rules.md#понятия)
  в другом смысле; поэтому здесь используется отдельное имя — бизнес-кейс (BC).
