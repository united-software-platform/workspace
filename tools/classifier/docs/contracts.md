## Входной контракт карточки

Файл JSON вне репозитория. `purpose` обязателен; `facets` опционален; неизвестные
поля игнорируются.

```json
{
  "name": "novamart-checkout",
  "purpose": "Сервис оформления заказа магазина NovaMart: корзина, оплата, подтверждение заказа",
  "facets": {
    "origin": "venture",
    "organization": "novamart",
    "group": "novamart-platform",
    "customer": null,
    "period": { "from": 2026, "to": null },
    "status": "active",
    "technologies": ["go", "postgresql", "kafka", "docker"],
    "domains": ["ecommerce"],
    "roles": ["developer"]
  }
}
```

Для векторизации берутся `purpose` и значимые фасеты без пустых: `domains`,
`technologies`, `roles`, `status`, `origin`. Остальные фасеты (`organization`,
`group`, `customer`, `period`) описывают административную принадлежность и в текст
сопоставления не входят.

## Выходной контракт классификации

JSON на stdout. Форма повторяет записи реестра классификаций SPCF: уровни, роли,
confidence, rationale, needs_confirmation.

```json
{
  "spcf": {
    "L1_application_domain": [
      { "id": "DOM-003", "role": "primary",   "confidence": 0.74 },
      { "id": "DOM-011", "role": "secondary", "confidence": 0.71 },
      { "id": "DOM-004", "role": "secondary", "confidence": 0.69 }
    ],
    "L2_activity_subdomain": [
      { "id": "SUB-004", "role": "primary",   "confidence": 0.72 }
    ],
    "L3_problem_domain": [
      { "id": "PRB-002", "role": "primary",   "confidence": 0.66 }
    ],
    "L4_solution_archetype": [
      { "id": "SOL-031", "role": "primary",   "confidence": 0.70 }
    ]
  },
  "needs_confirmation": true,
  "reasons": ["top-1 L2 (SUB-004) ниже порога 0.5"],
  "rationale": "Сопоставление по purpose и значимым фасетам; уровень L2 ниже порога — данных карточки для подобласти недостаточно."
}
```

Поля контракта:

- `spcf` — по каждому уровню L1–L4 список кандидатов, упорядоченных по убыванию
  confidence; первый — `primary`, последующие до 3 на уровень — `secondary`;
- `confidence` — косинусная близость вектора карточки к вектору записи таксономии,
  0–1, округление до 4 знаков;
- `needs_confirmation` — true при пустом `purpose`, когда primary хотя бы одного
  уровня ниже порога или когда отрыв primary от второго кандидата уровня меньше
  margin (константа утилиты, 0.02);
- `reasons` — машинно-читаемые причины needs_confirmation: какие уровни/записи ниже
  порога, где отрыв меньше margin или почему данных мало; уровень с единственным
  кандидатом отрыва не даёт;
- `rationale` — человекочитаемое пояснение итога одним предложением;
- `threshold` в контракт не входит: это параметр вызова, а не свойство результата.

Формат rationale утверждён свободным текстом (открытый вопрос design D6/OQ разрешён
здесь): сценарий формирует его из состава уровней и причин, без жёсткой структуры.

## Переменные окружения

| Имя | Назначение | Пример значения |
|-----|------------|-----------------|
| `EMBEDDINGS_BASE_URL` | Адрес прокси-эндпоинта embeddings | `http://proxy.example.internal:8000/v1` |
| `EMBEDDINGS_API_KEY` | Ключ доступа к эндпоинту | `secret` (вне git) |
| `EMBEDDINGS_MODEL` | Идентификатор модели | `ollama-local/embeddinggemma-2:latest` |

Контракт запроса — OpenAI-совместимый `POST {EMBEDDINGS_BASE_URL}/embeddings`,
тело `{"model": ..., "input": [тексты]}`, заголовок `Authorization: Bearer <ключ>`.
Ответ — `{"data": [{"index": i, "embedding": [...]}, ...]}`.
