# formular-operation Specification

## Purpose

Операция беклога `formular` и навык-обёртка `formular`: формирование бизнес-требования
прожаркой в карточку BR из девяти полей со стоп-знаком принятия владельцем и фиксацией
принятой карточки артефактом `docs/requirements/<ID>.md` — от сырой формулировки до
требования-документа одним вызовом.

## Requirements

### Requirement: Шаблон операции formular

Репозиторий SHALL содержать шаблон операции беклога `formular` в `templates/formular.md`;
порождение беклога идёт командой `backlog generate --operation formular`, исполнение —
навыком `/backlog:backlog-run` по общему порядку исполнения беклогов. Шаблон SHALL проходить
приёмку `backlog check-template` с кодом возврата `0`.

#### Scenario: Порождение беклога formular

- **WHEN** исполнитель вызывает `backlog generate --operation formular` с предметом и значением `requirement`
- **THEN** в `backlog/formular/<предмет>/tasks.md` появляется беклог по шаблону, несущий `requirement` во фронтматтере

#### Scenario: Шаблон принят ядром

- **WHEN** прогоняют `backlog check-template templates/formular.md`
- **THEN** код возврата `0` — расхождений с грамматикой шаблонов нет

### Requirement: Значения операции formular

Операция formular SHALL принимать значение `requirement` — исходную формулировку владельца —
и несёт его во фронтматтере порождённого беклога. Карточка BR — рабочее значение `br_card`
во фронтматтере на время прогона; продукт операции — артефакт требования
в `docs/requirements/`. Значение `target` операция не принимает: с GitHub она не работает.

#### Scenario: Второй сбор значений не нужен

- **WHEN** беклог formular исполнен после прерывания
- **THEN** исполнитель читает `requirement` и `br_card` из фронтматтера и не спрашивает значения заново

### Requirement: Прожарка BR по шаблону карточки

Беклог formular SHALL содержать задачу прожарки требования через `/mattpocock-skills:grilling`
по девяти полям карточки: ID (вида `BR-NNN`), Name, Description, Rationale, Business Outcome,
Success Criteria, Priority (`Must` / `Should` / `Could` / `Won't`), Status, Source. Прожарка
MUST уточнять формулировки, пока каждое поле не заполнено; выдумывать содержимое полей
запрещено — недостающее выясняется у владельца. Заполненная карточка записывается
во фронтматтер значением `br_card`.

#### Scenario: Прожарка заполняет все поля

- **WHEN** прожарка завершена
- **THEN** `br_card` несёт все девять полей, и каждое заполнено словами владельца, а не выдумано исполнителем

#### Scenario: Поле без сведений

- **WHEN** у владельца нет сведений для поля (например, Source)
- **THEN** исполнитель спрашивает владельца и вносит ответ; вопрос не снимается пометкой «нет» без ответа владельца

### Requirement: Линтинг карточки перед стоп-знаком

Беклог formular SHALL прогонять собранную карточку линтером формулировок —
`tools/reqlint/reqlint.py` с правилами `tools/reqlint/rules.yml`: значения полей карточки
подаются по строке на поле. Находки severity `error` MUST называться на стоп-знаке
с решением владельца по каждой: устранить правкой карточки либо принять с обоснованием,
записанным в беклог. Линтер не заменяет прожарку и сам по себе принятие не запрещает.

#### Scenario: Линтер прогнан по полям карточки

- **WHEN** карточка собрана значением `br_card`
- **THEN** значения полей прогнаны линтером, находки известны к стоп-знаку

#### Scenario: Блокирующие находки названы на стоп-знаке

- **WHEN** линтер вернул находки severity `error`
- **THEN** стоп-знак называет каждую и фиксирует решение владельца: устранена правкой карточки либо принята с обоснованием

#### Scenario: Чистый прогон

- **WHEN** линтер не вернул находок
- **THEN** стоп-знак сообщает чистый вердикт линтера

### Requirement: Статусы карточки на стоп-знаке

Беклог formular SHALL останавливаться на стоп-знаке после прожарки: показать владельцу карточку
`br_card` целиком по девяти полям. Карточка рождается в статусе `Draft`; принятие владельцем
переводит Status в `Proposed`, отказ — в `Rejected`, и карточка с вердиктом остаётся в беклоге.
Подтверждение фиксируется во фронтматтере. Режима авто нет: без явного принятия карточка
не считается сформированной. Статусы `Approved` и `Deprecated` операция не назначает.

#### Scenario: Принятие карточки

- **WHEN** владелец подтверждает показанную карточку на стоп-знаке
- **THEN** Status карточки становится `Proposed`, подтверждение записано во фронтматтер, беклог идёт к фиксации артефакта

#### Scenario: Отказ владельца

- **WHEN** владелец отклоняет карточку
- **THEN** Status карточки становится `Rejected`, беклог останавливается, карточка и причина отказа остаются в беклоге

### Requirement: Артефакт требования в docs/requirements

Принятая карточка SHALL фиксироваться артефактом `docs/requirements/<ID>.md`: имя файла — ID
карточки; файл несёт все девять полей и следует правилам документации репозитория (заголовок,
назначение, навигация, таблица версий). Артефакт коммитится в репозиторий — требование доступно
для работы вне прогона. Отклонённая карточка артефакт не получает: `Rejected` остаётся только
в беклоге. Занятость номеров BR-NNN определяется по файлам каталога `docs/requirements/`.

#### Scenario: Принятая карточка становится документом

- **WHEN** владелец принял карточку на стоп-знаке
- **THEN** в `docs/requirements/` появляется файл `<ID>.md` со всеми девятью полями и статусом `Proposed`

#### Scenario: Отклонённая карточка файла не получает

- **WHEN** владелец отклонил карточку
- **THEN** файл в `docs/requirements/` не создаётся, карточка остаётся в беклоге прогона

### Requirement: Границы операции

Операция formular MUST NOT создавать задачи на GitHub, ветки изменений и коммиты: её продукт —
артефакт требования в `docs/requirements/`. Заведение задачи и ветки по принятому требованию —
операции `workflow`, вызываемые отдельно.

#### Scenario: Прогон не трогает GitHub

- **WHEN** беклог formular исполнен от начала до итога
- **THEN** задач на GitHub не создано, ветка не открыта

### Requirement: Вход навыка formular

Навык `formular` SHALL принимать требование владельца текстом вызова; пустой вызов получает
ровно один вопрос о требовании. Репозиторий SHALL нести навык в `.claude/skills/formular/SKILL.md`
и `.zcode/skills/formular/SKILL.md` с одинаковым содержанием.

#### Scenario: Пустой вызов

- **WHEN** навык `formular` вызван без требования
- **THEN** владелец получает ровно один вопрос о требовании, и после ответа навык продолжается без повторных вопросов

#### Scenario: Навыки двух точек входа не расходятся

- **WHEN** сравнивают `.claude/skills/formular/SKILL.md` и `.zcode/skills/formular/SKILL.md`
- **THEN** содержание файлов одинаково

### Requirement: Делегирование навыка formular

Навык `formular` SHALL строить предмет `{YYYYMMDDHHMMSS}-{slug}` и делегировать порождение
`/backlog:backlog-generate` с операцией `formular` и значением `requirement`; собранный вызов
`backlog generate` MUST показываться владельцу до прогона. После порождения навык SHALL передавать
исполнение `/backlog:backlog-run` без повторного вопроса.

#### Scenario: Один вызов от требования до карточки

- **WHEN** владелец вызывает навык `formular` с текстом требования
- **THEN** навык порождает беклог операции formular и передаёт его исполнение; стоп-знак принятия карточки спрашивает владельца всегда
