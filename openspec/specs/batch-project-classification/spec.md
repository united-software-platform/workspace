# batch-project-classification Specification

## Purpose

Пакетная классификация проектов: один опрос владельца собирает список проектов, фоновые агенты-исполнители на модели haiku классифицируют каждый проект без остановок, итог — один JSON-файл на прогон.

## Requirements

### Requirement: Навык пакетной классификации
Репозиторий SHALL содержать навык `classify-batch`, принимающий вызов без значений, опрашивающий владельца и формирующий список проектов до полного принятия итогового состава; после принятия навык запускает классификацию всех проектов списка.

#### Scenario: Опрос до принятия списка
- **WHEN** владелец вызывает навык `classify-batch` и называет проекты
- **THEN** навык показывает итоговый состав списка и продолжает опрос до явного принятия владельцем

#### Scenario: Запуск классификации после принятия
- **WHEN** владелец принял список проектов
- **THEN** навык запускает классификацию каждого проекта списка фоновыми агентами на выбранной модели исполнителя

### Requirement: Выбор модели исполнителя
Навык SHALL спрашивать модель исполнителя при опросе до запуска агентов: уровни haiku (умолчание), sonnet, opus, fable. Конкретная модель уровня SHALL разрешаться платформой через переменную окружения `ANTHROPIC_DEFAULT_<УРОВЕНЬ>_MODEL`. Выбранный уровень SHALL передаваться в беклоги элементов значением `runner_model`; авторство решений исполнителя-автомата SHALL записываться именем выбранного уровня.

#### Scenario: Владелец не назвал модель
- **WHEN** владелец принял список, не назвав модель исполнителя
- **THEN** агенты запускаются на уровне haiku, авторство решений записывается как `haiku`

#### Scenario: Владелец выбрал уровень sonnet
- **WHEN** владелец назвал уровень sonnet при опросе
- **THEN** агенты запускаются на уровне sonnet, авторство решений записывается как `sonnet`

### Requirement: Автоматический шаблон операции
Репозиторий SHALL содержать шаблон операции `classify-project-auto`, порождающий беклог без маркеров «Стоп-знак.» автоматического прогона классификации проекта: поиск источников по названию проекта, выбор источника исполнителем-автоматом, составление карточки, прямой вызов утилиты классификации, фиксация принятия исполнителем-автоматом. Решения исполнителя-автомата и их авторство (значение `runner_model`) SHALL записываться во фронтматтер беклога.

#### Scenario: Порождение беклога авто-операции
- **WHEN** фоновый агент исполняет операцию `classify-project-auto` для проекта списка
- **THEN** порождается беклог, задачи которого не содержат маркеров «Стоп-знак.», а решения с авторством фиксируются во фронтматтере

#### Scenario: Прямой вызов утилиты классификации
- **WHEN** беклог авто-операции доходит до классификации карточки
- **THEN** утилита классификации вызывается напрямую, без порождения вложенного беклога `classify`

### Requirement: Автопринятие на чистом результате
Автопринятие классификации SHALL действовать только на чистом результате утилиты; записи с `needs_confirmation` SHALL получать статус `failed` с причиной `needs_confirmation`, данные классификации при этом сохраняются в записи прогона.

#### Scenario: Чистый результат
- **WHEN** утилита вернула результат без `needs_confirmation`
- **THEN** исполнитель-автомат принимает классификацию, авторство принятия фиксируется во фронтматтере

#### Scenario: Результат требует подтверждения
- **WHEN** утилита вернула результат с `needs_confirmation`
- **THEN** проект получает статус `failed` с причиной `needs_confirmation`, данные классификации сохраняются в записи прогона

### Requirement: Автопринятие A и B-метки
Итог утилиты с объединённой меткой уровня «A & B» — кандидаты в пределах margin, соединённые общей меткой, код возврата `0` — SHALL считаться чистым результатом: элемент получает статус `classified`, метка фиксируется как принятая классификация.

#### Scenario: Метка A и B принята авто-режимом
- **WHEN** утилита вернула код `0` с объединённой меткой уровня «A & B» по кандидатам в пределах margin
- **THEN** элемент получает статус `classified`, метка фиксируется как принятая классификация

#### Scenario: Отказ остаётся только для порога
- **WHEN** утилита вернула `needs_confirmation` по непройденному порогу confidence
- **THEN** элемент получает статус `failed` с причиной `needs_confirmation`, данные классификации сохраняются в записи прогона

### Requirement: Поиск источников в авто-режиме
Поиск источников в авто-режиме SHALL продолжаться при одном и более найденных результатах — исполнитель-автомат выбирает источник из найденных, фактическое число результатов фиксируется в записи прогона; ноль найденных результатов SHALL давать проекту статус `failed` с причиной «поиск не дал результатов».

#### Scenario: Недобор результатов поиска
- **WHEN** веб-поиск по названию проекта вернул три результата вместо пяти
- **THEN** исполнитель-автомат выбирает источник из трёх найденных, число 3 фиксируется в записи прогона

#### Scenario: Поиск без результатов
- **WHEN** веб-поиск по названию проекта не вернул результатов
- **THEN** проект получает статус `failed` с причиной «поиск не дал результатов»

### Requirement: Итоговый файл прогона
Прогон SHALL завершаться одним файлом `projects/{YYYYMMDDHHMMSS}.json` — штамп локального времени запуска прогона; файл пишет оркестратор один раз по завершении всех агентов. Запись по проекту SHALL содержать: имя проекта, выбранный источник (URL), карточку (`purpose`, `facets`), принятую классификацию, статус (`classified` / `failed`) и причину при неудаче.

#### Scenario: Итоговый файл по завершении
- **WHEN** все фоновые агенты прогона завершились
- **THEN** оркестратор пишет единственный файл `projects/{YYYYMMDDHHMMSS}.json` с записью по каждому проекту списка

#### Scenario: Состав записи прогона
- **WHEN** оркестратор пишет запись упавшего проекта
- **THEN** запись содержит имя проекта, статус `failed` и причину падения

### Requirement: Карточки прогона
Карточки проектов прогона SHALL храниться в `projects/{штамп}.cards/item-NN.json` — по одной карточке на проект, внутри игнорируемого git каталога `projects/`.

#### Scenario: Карточка проекта в каталоге прогона
- **WHEN** агент составил карточку проекта для классификации
- **THEN** карточка сохраняется как `projects/{штамп}.cards/item-NN.json`

### Requirement: Порог классификации на пакет
Прогон SHALL применять единый порог confidence на весь пакет: по умолчанию 0.5; владелец вправе назвать свой порог при опросе — тогда он один на все проекты прогона.

#### Scenario: Владелец не назвал порог
- **WHEN** владелец принял список проектов, не назвав порог
- **THEN** все проекты прогона классифицируются с порогом 0.5

#### Scenario: Владелец назвал порог
- **WHEN** владелец назвал порог 0.7 при опросе
- **THEN** все проекты прогона классифицируются с порогом 0.7

### Requirement: Устойчивость прогона к падению проекта
Падение одного проекта SHALL НЕ останавливать прогон: упавший проект фиксируется в итоговом файле статусом `failed` с причиной; прогон успешен, когда обработан каждый проект списка.

#### Scenario: Один проект из трёх упал
- **WHEN** классификация второго проекта из трёх завершилась ошибкой
- **THEN** первый и третий проекты обрабатываются, второй фиксируется статусом `failed` с причиной ошибки

### Requirement: Сводный отчёт по выборам
По завершении прогона владелец SHALL получать сводный отчёт по автоматическим выборам на точках решений: выбранные источники и принятые классификации по каждому проекту.

#### Scenario: Отчёт после прогона
- **WHEN** оркестратор завершил все проекты и написал итоговый файл
- **THEN** владелец получает сводный отчёт по выборам источников и принятым классификациям

### Requirement: Приватность прогона
Прогон SHALL хранить реальные имена проектов только во фронтматтере беклогов и итоговом файле; предмет беклога — `{штамп пакета}-item-{NN}` без реального имени; каталоги беклогов пакетного прогона и `projects/` не коммитятся.

#### Scenario: Имя каталога беклога без имени проекта
- **WHEN** фоновый агент порождает беклог авто-операции
- **THEN** предмет беклога имеет вид `{штамп пакета}-item-{NN}`, реальное имя проекта живёт только во фронтматтере

### Requirement: Цикл дополнения в авто-режиме
При коде возврата `1` (`needs_confirmation`) беклог авто-операции SHALL исполнять цикл дополнения: анализ `reasons`, дополнение карточки данными выбранного источника и повторный вызов утилиты, до трёх попыток в одном беклоге.

#### Scenario: Дополнение развело кандидатов
- **WHEN** первый вызов утилиты вернул код `1`, а после дополнения карточки повторный вызов вернул код `0`
- **THEN** классификация принимается исполнителем-автоматом, попытка дополнения фиксируется во фронтматтере

#### Scenario: Три попытки не помогли
- **WHEN** все три вызова утилиты вернули код `1`
- **THEN** элемент получает статус `failed` с причиной `needs_confirmation`, запись прогона несёт данные последней классификации

#### Scenario: Карточка перезаписывается на месте
- **WHEN** исполнитель-автомат дополняет карточку по спорным уровням из `reasons`
- **THEN** карточка перезаписывается по пути `projects/{штамп}.cards/item-NN.json`, счётчик и ход дополнений фиксируются во фронтматтере беклога

#### Scenario: Ошибка окружения не дополняется
- **WHEN** утилита вернула код `2`
- **THEN** элемент завершается отказом с причиной ошибки, цикл дополнения не запускается
