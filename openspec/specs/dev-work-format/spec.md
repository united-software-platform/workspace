# dev-work-format Specification

## Purpose

Контракт реализованной работы разработчика: структура YAML-выгрузки работы одного человека или команды
из git-истории репозитория, где каждый коммит связан с кодом из слепка tldr по нормализованному пути
файла. Изменение описывает только формат — извлечение выгрузки остаётся за пределами.

## Requirements

### Requirement: Структура YAML-контракта работы

Формат SHALL быть YAML-документом со шапкой и списком записей коммитов, описанным в
`docs/work-format.md`. Шапка MUST содержать: версию формата, дату формирования выгрузки, ссылку
на реестр идентичностей, параметр выборки (`person: <slug>` или `team: <имя>`), вошедших в выборку
лиц, период, линию истории, имя слепка и дату его съёмки, оговорку о неизвестной ревизии слепка,
границы области с счётчиком путей вне области.

#### Scenario: Выгрузка одного разработчика

- **WHEN** выборка задана `person` с реестром, где у человека два email
- **THEN** шапка содержит параметр выборки, это лицо и оба email, а записи покрывают все его коммиты,
  включая merge

#### Scenario: Шапка без периода

- **WHEN** выгрузка сформирована без ограничения периода
- **THEN** поля периода в шапке отсутствуют, что означает всю историю линии

### Requirement: Выборка по человеку или команде через реестр идентичностей

Реестр идентичностей SHALL задавать каждому разработчику slug, имя, список email и команду; выборка
MUST задаваться `person: <slug>` или `team: <имя>`. В выгрузку MUST попадать коммиты, email автора
которых входит в список email лица; один человек с несколькими email SHALL представляться одной
записью реестра со списком email. Коммитимый шаблон `docs/people.yaml` MUST содержать только
вымышленные записи-примеры, структурно идентичные реальным.

#### Scenario: Человек с несколькими email

- **WHEN** лицо реестра имеет два email и коммитило под обоими
- **THEN** обе серии коммитов входят в одну выборку этого лица

#### Scenario: Срез по команде

- **WHEN** выборка задана `team: backend`
- **THEN** выгрузка включает коммиты всех лиц, чьи записи реестра принадлежат этой команде

### Requirement: Единица работы — коммит с типологией

Единицей работы SHALL быть отдельный коммит, включая merge-коммиты. Каждая запись MUST нести
`kind: code` для коммита кода и `kind: integration` для merge-коммита; для integration MUST
указываться `merged: own | others` — вливались ли ветки, все коммиты которых принадлежат самому
автору merge (`own`), или ветки с коммитами других авторов (`others`). Поля ревью формат
MUST NOT содержать: «отревьюировал» — интерпретация потребителя.

#### Scenario: Merge чужой ветки

- **WHEN** автор выполняет merge, вторая родительская ветка которого содержит коммиты других авторов
- **THEN** запись имеет `kind: integration`, `merged: others`

#### Scenario: Собственный коммит кода

- **WHEN** коммит выполнен без второго родителя
- **THEN** запись имеет `kind: code` и статус-лист затронутых путей

### Requirement: Статус-лист путей и numstat в записи коммита

Запись коммита SHALL содержать sha, дату, заголовок, тело при наличии, статус-лист затронутых путей
с пометкой A/M/D/R и числом добавленных/удалённых строк (numstat); удалённые пути MUST фиксироваться
явно. Код задачи и имя ветки — плавающий источник истины: формат MAY нести их как опциональные
аннотации без гарантий покрытия.

#### Scenario: Коммит с удалением файла

- **WHEN** коммит автора удаляет файл из области
- **THEN** статус-лист записи содержит этот путь с пометкой `D` и numstat

#### Scenario: Коммит без кода задачи

- **WHEN** заголовок коммита не содержит кода задачи и имя ветки не определено
- **THEN** запись не несёт аннотаций кода задачи и ветки, остальные поля присутствуют

### Requirement: Пара коммит—слепок по нормализованному пути

Формат SHALL связывать каждый затронутый коммитом путь с кодом слепка по нормализованному POSIX-пути
файла. Нормализация MUST отрезать ведущий `./` и префикс `/project/` из путей слепка. Пара MUST
означать «путь присутствует в слепке», а не «код родился этим коммитом»: ревизия слепка неизвестна,
и шапка выгрузки MUST нести дату съёмки слепка и оговорку о неизвестной ревизии.

#### Scenario: Путь слепка с префиксом /project/

- **WHEN** путь в отчёте слепка имеет вид `/project/src/Service/A.php`
- **THEN** после нормализации он связывается с git-путём `src/Service/A.php`

#### Scenario: Путь удалён до съёмки слепка

- **WHEN** коммит трогал путь, которого нет в слепке
- **THEN** пара помечена «в слепке не найдено», путь остаётся в записи коммита

### Requirement: Аннотации слепка в паре

Пара для пути, найденного в слепке, MAY нести опциональные аннотации слепка: символы (классы, методы
с диапазонами строк) из `03-structure.json` — по имени символа, не по номерам строк; агрегаты истории
и метрики качества — по нужде потребителя. Ядром связки SHALL быть `01-tree.json` (существование
пути) и `03-structure.json` (символы).

#### Scenario: Файл с классами и методами

- **WHEN** парный путь найден в `03-structure.json` и содержит класс с методами
- **THEN** пара несёт опциональную аннотацию символов с именами и диапазонами строк слепка

#### Scenario: Путь есть только в дереве

- **WHEN** парный путь найден в `01-tree.json`, но отсутствует в `03-structure.json`
- **THEN** пара несёт пометку «найден», без аннотации символов

### Requirement: JSON-проекция канонического контракта

Формат SHALL допускать производную JSON-проекцию для загрузки в Elastic и реляционное хранилище;
конверсия MUST быть детерминированной и описанной в `docs/work-format.md`. Схемы хранения
(ES-mapping, DDL) — задача потребителя и в спецификацию формата не входят.

#### Scenario: Выгрузка в JSON

- **WHEN** проекция выгрузки сформирована в JSON
- **THEN** она структурно идентична YAML-контракту и конвертируется в него без потерь

### Requirement: Частные данные не попадают в репозиторий

Коммитимые артефакты формата (спецификация, шаблон реестра) MUST содержать только вымышленные данные,
структурно идентичные реальным. Реальные выгрузки и реальный реестр идентичностей — локальные файлы
вне git.

#### Scenario: Шаблон реестра в репозитории

- **WHEN** шаблон `docs/people.yaml` открыт после реализации изменения
- **THEN** он содержит только вымышленные записи-примеры и структуру, совпадающую с реестром

#### Scenario: Спецификация формата

- **WHEN** `docs/work-format.md` прочитан после реализации изменения
- **THEN** он не содержит имён, email, путей и идентификаторов проект-источника
