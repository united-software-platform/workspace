# requirement-add-operation Specification

## Purpose

Операция беклога `requirement-add` и навык-обёртка `requirement-add`: формирование
бизнес-требования прожаркой в карточку BR из девяти полей со стоп-знаком принятия владельцем
и фиксацией принятой карточки артефактом `docs/requirements/<ID>.md` — от сырой формулировки
до требования-документа одним вызовом.

## Requirements

### Requirement: Шаблон операции requirement-add

Репозиторий SHALL содержать шаблон операции беклога `requirement-add`
в `templates/requirement-add.md`; порождение беклога идёт командой
`backlog generate --operation requirement-add`, исполнение — навыком `/backlog:backlog-run`
по общему порядку исполнения беклогов. Шаблон SHALL проходить приёмку `backlog check-template`
с кодом возврата `0`.

#### Scenario: Порождение беклога requirement-add

- **WHEN** исполнитель вызывает `backlog generate --operation requirement-add` с предметом и значением `requirement`
- **THEN** в `backlog/requirement-add/<предмет>/tasks.md` появляется беклог по шаблону, несущий `requirement` во фронтматтере

#### Scenario: Шаблон принят ядром

- **WHEN** прогоняют `backlog check-template templates/requirement-add.md`
- **THEN** код возврата `0` — расхождений с грамматикой шаблонов нет

### Requirement: Значения операции requirement-add

Операция requirement-add SHALL принимать значение `requirement` — исходную формулировку
владельца — и несёт его во фронтматтере порождённого беклога. Карточка BR — рабочее значение
`br_card` во фронтматтере на время прогона; продукт операции — артефакт требования
в `docs/requirements/`. Значение `target` операция не принимает: с GitHub она не работает.

#### Scenario: Второй сбор значений не нужен

- **WHEN** беклог requirement-add исполнен после прерывания
- **THEN** исполнитель читает `requirement` и `br_card` из фронтматтера и не спрашивает значения заново

### Requirement: Контекст глоссария в прогоне

Беклог requirement-add SHALL содержать предусловие обязательного чтения `GLOSSARY.md` —
единственного источника канонических понятий домена — и добавления его в контекст прогона
до выявления требования. Понятие формулировки вне глоссария — кандидат в новые понятия
доменной сверки.

#### Scenario: Глоссарий в контексте до прожарки

- **WHEN** беклог requirement-add начинает группу прожарки
- **THEN** `GLOSSARY.md` прочитан целиком и находится в контексте исполнителя: канонические имена и Avoid-имена понятий домена известны

#### Scenario: Глоссария нет — прогон не начинается

- **WHEN** файл `GLOSSARY.md` в корне репозитория отсутствует
- **THEN** исполнение останавливается до выявления требования, владельцу называется препятствие

### Requirement: Доменная сверка предмета и терминов

Беклог requirement-add SHALL содержать задачу доменной сверки между выявлением требования
и прожаркой: предмет по смыслу сверяется с существующими BR из `docs/requirements/`, термины
формулировки — с `GLOSSARY.md`. При введении новых понятий исполнитель SHALL вызвать навык
`/mattpocock-skills:domain-modeling` и согласовать их с текущим доменом. Вердикт сверки
MUST называться на стоп-знаке принятия.

#### Scenario: Новый предмет

- **WHEN** сверка не нашла предмет в `docs/requirements/`, термины согласованы с доменом
- **THEN** прогон продолжает формирование нового BR, вердикт сверки — «новый предмет»

#### Scenario: Термин получает каноническое имя

- **WHEN** формулировка использует понятие, уже определённое в `GLOSSARY.md` под другим именем
- **THEN** поля карточки заполняются каноническим именем понятия из глоссария

#### Scenario: Дубль предмета

- **WHEN** предмет требования по смыслу совпадает с существующим BR из `docs/requirements/`
- **THEN** новый BR не заводится — прогон ведёт правку существующего BR новой версией по правилам документации, ID требования не меняется

#### Scenario: Новые понятия согласованы с доменом

- **WHEN** формулировка вводит понятия, отсутствующие в `GLOSSARY.md`
- **THEN** вызван навык `/mattpocock-skills:domain-modeling`, понятия согласованы с предметами, сущностями, доменными службами и атрибутами текущего домена по классификации глоссария, предложенные статьи глоссария названы на стоп-знаке

### Requirement: Прожарка BR по шаблону карточки

Беклог requirement-add SHALL содержать задачу вызова навыка `/mattpocock-skills:grilling`
с передачей намерения — значения `requirement` фронтматтера и краткой формулировки: навык
ведёт прожарку раундами вопросов фронтира с рекомендованными ответами, факты выясняет сам,
решения остаются за владельцем, конец — пустой фронтир и подтверждённое общее понимание.
Ответы раундов исполнитель разносит по девяти полям карточки: ID (вида `BR-NNN`), Name,
Description, Rationale, Business Outcome, Success Criteria, Priority (`Must` / `Should` /
`Could` / `Won't`), Status, Source. Прожарка MUST продолжаться, пока фронтир не пуст и каждое
поле не заполнено; выдумывать содержимое полей запрещено — недостающее выясняется у владельца.
Заполненная карточка записывается во фронтматтер значением `br_card`.

#### Scenario: Намерение передано навыку

- **WHEN** задача прожарки исполняется
- **THEN** навык `/mattpocock-skills:grilling` вызван со значением `requirement` и краткой формулировкой, раунды вопросов идут до пустого фронтира

#### Scenario: Прожарка заполняет все поля

- **WHEN** прожарка завершена
- **THEN** `br_card` несёт все девять полей, и каждое заполнено словами владельца, а не выдумано исполнителем

#### Scenario: Поле без сведений

- **WHEN** у владельца нет сведений для поля (например, Source)
- **THEN** исполнитель спрашивает владельца и вносит ответ; вопрос не снимается пометкой «нет» без ответа владельца

### Requirement: Линтинг карточки перед стоп-знаком

Беклог requirement-add SHALL прогонять собранную карточку линтером формулировок —
`tools/reqlint/reqlint.py` с правилами `tools/reqlint/rules.yml`: значения полей карточки
подаются по строке на поле. Находки severity `error` MUST называться на стоп-знаке
с решением владельца по каждой: устранить правкой карточки либо принять с обоснованием,
записанным в беклог. Линтер не заменяет прожарку и сам по себе принятие не запрещает.

#### Scenario: Линтер прогнан по полям карточки

- **WHEN** карточка собрана значением `br_card`
- **THEN** значения полей прогнаны линтером, находки известны к стоп-знаку

#### Scenario: Блокирующие находки названы на стоп-знаке

- **WHEN** линтер вернул находки severity `error`
- **THEN** стоп-знак называет каждую и фиксирует решение владельца: устранена правкой карточки либо принята с обоснованием

#### Scenario: Чистый прогон

- **WHEN** линтер не вернул находок
- **THEN** стоп-знак сообщает чистый вердикт линтера

### Requirement: Статусы карточки на стоп-знаке

Беклог requirement-add SHALL останавливаться на стоп-знаке после прожарки: показать владельцу
карточку `br_card` целиком по девяти полям. Карточка рождается в статусе `Draft`; принятие
владельцем переводит Status в `Proposed`, отказ — в `Rejected`, и карточка с вердиктом остаётся
в беклоге. Подтверждение фиксируется во фронтматтере. Режима авто нет: без явного принятия
карточка не считается сформированной. Статусы `Approved` и `Deprecated` операция не назначает.

#### Scenario: Принятие карточки

- **WHEN** владелец подтверждает показанную карточку на стоп-знаке
- **THEN** Status карточки становится `Proposed`, подтверждение записано во фронтматтер, беклог идёт к фиксации артефакта

#### Scenario: Отказ владельца

- **WHEN** владелец отклоняет карточку
- **THEN** Status карточки становится `Rejected`, беклог останавливается, карточка и причина отказа остаются в беклоге

### Requirement: Артефакт требования в docs/requirements

Принятая карточка SHALL фиксироваться артефактом `docs/requirements/<ID>.md`: имя файла — ID
карточки; файл несёт все девять полей и следует правилам документации репозитория (заголовок,
назначение, навигация, таблица версий). Артефакт коммитится в репозиторий — требование доступно
для работы вне прогона. Отклонённая карточка артефакт не получает: `Rejected` остаётся только
в беклоге. Занятость номеров BR-NNN определяется по файлам каталога `docs/requirements/`.

#### Scenario: Принятая карточка становится документом

- **WHEN** владелец принял карточку на стоп-знаке
- **THEN** в `docs/requirements/` появляется файл `<ID>.md` со всеми девятью полями и статусом `Proposed`

#### Scenario: Отклонённая карточка файла не получает

- **WHEN** владелец отклонил карточку
- **THEN** файл в `docs/requirements/` не создаётся, карточка остаётся в беклоге прогона

### Requirement: Границы операции

Операция requirement-add MUST NOT создавать задачи на GitHub, ветки изменений и коммиты:
её продукт — артефакт требования в `docs/requirements/`. Заведение задачи и ветки по принятому
требованию — операции `workflow`, вызываемые отдельно.

#### Scenario: Прогон не трогает GitHub

- **WHEN** беклог requirement-add исполнен от начала до итога
- **THEN** задач на GitHub не создано, ветка не открыта

### Requirement: Вход навыка requirement-add

Навык `requirement-add` SHALL принимать требование владельца текстом вызова; пустой вызов
получает ровно один вопрос о требовании. Репозиторий SHALL нести навык
в `.claude/skills/requirement-add/SKILL.md` и `.zcode/skills/requirement-add/SKILL.md`
с одинаковым содержанием.

#### Scenario: Пустой вызов

- **WHEN** навык `requirement-add` вызван без требования
- **THEN** владелец получает ровно один вопрос о требовании, и после ответа навык продолжается без повторных вопросов

#### Scenario: Навыки двух точек входа не расходятся

- **WHEN** сравнивают `.claude/skills/requirement-add/SKILL.md` и `.zcode/skills/requirement-add/SKILL.md`
- **THEN** содержание файлов одинаково

### Requirement: Делегирование навыка requirement-add

Навык `requirement-add` SHALL строить предмет `{YYYYMMDDHHMMSS}-{slug}` и делегировать
порождение `/backlog:backlog-generate` с операцией `requirement-add` и значением
`requirement`; собранный вызов `backlog generate` MUST показываться владельцу до прогона.
После порождения навык SHALL передавать исполнение `/backlog:backlog-run` без повторного
вопроса.

#### Scenario: Один вызов от требования до карточки

- **WHEN** владелец вызывает навык `requirement-add` с текстом требования
- **THEN** навык порождает беклог операции requirement-add и передаёт его исполнение; стоп-знак принятия карточки спрашивает владельца всегда

### Requirement: Правила классов дефектов в линтере

Правила `tools/reqlint/rules.yml` SHALL покрывать лексически проверимые классы дефектов
требований наряду с существующими: категорию «рецепт реализации» — формулировка диктует
техническое решение, а не потребность, — и правило измеримости — строка критерия без числа
и порога. Правила декларативные, схемы `{name, pattern, hint, error}`; `reqlint.py` не меняется.

#### Scenario: Рецепт реализации помечен

- **WHEN** строка поля карточки содержит маркер решения — например «реализовать через», «использовать postgres», «создать таблицу»
- **THEN** линтер возвращает находку категории «рецепт реализации» с подсказкой вынести решение из требования в дизайн

#### Scenario: Критерий без порога помечен

- **WHEN** строка критерия говорит об успехе или проверке, но не содержит ни числа, ни порога, ни чек-листа
- **THEN** линтер возвращает находку правила измеримости с подсказкой назвать число, единицу и процедуру проверки

#### Scenario: Формулировка без маркеров чиста

- **WHEN** строка поля не содержит маркеров новых правил
- **THEN** новые правила не дают по ней находок — вердикт линтера не меняется

### Requirement: Семантическая проверка карточки

Беклог requirement-add SHALL содержать задачу семантической проверки собранной карточки после
линтинга: исполнитель проверяет карточку целиком по рубрике четырёх классов дефектов —
неполнота, двусмысленность, противоречие, рецепт реализации, — включая отношения полей друг
к другу (Description, Business Outcome, Success Criteria) и критериев друг к другу внутри
Success Criteria. Выход — находки вида `{класс, цитата, уточняющий вопрос}` либо чистый вердикт.

#### Scenario: Противоречие между критериями найдено

- **WHEN** критерии Success Criteria противоречат друг другу — например, один требует «за любой период», другой задаёт фиксированный период
- **THEN** семантическая проверка возвращает находку класса «противоречие» с цитатами обоих критериев и уточняющим вопросом владельцу

#### Scenario: Рецепт реализации в Description найден

- **WHEN** Description диктует техническое решение, а не описывает потребность бизнеса
- **THEN** семантическая проверка возвращает находку класса «рецепт реализации» с цитатой и уточняющим вопросом о настоящей потребности

#### Scenario: Пробел между полями найден

- **WHEN** Business Outcome не покрыт ни одним критерием Success Criteria
- **THEN** семантическая проверка возвращает находку класса «неполнота» с указанием непокрытой части исхода

#### Scenario: Чистая карточка

- **WHEN** рубрика не даёт находок ни по одному классу
- **THEN** семантическая проверка возвращает чистый вердикт, который стоп-знак называет наряду с вердиктом линтера

### Requirement: Стоп-знак сводит вердикты трёх уровней

Стоп-знак принятия SHALL называть вердикты трёх уровней: находки линтера severity `error`,
семантические находки любого класса и вердикт доменной сверки. Каждая названная находка
MUST получить решение владельца: устранить правкой карточки с повторением прогонов либо
принять с обоснованием, записанным в беклог. Без решения по каждой названной находке
и по вердикту сверки принятие не происходит.

#### Scenario: Оба вердикта на стоп-знаке

- **WHEN** владельцу показывают карточку на стоп-знаке
- **THEN** названы находки линтера severity `error` и семантические находки всех классов, по каждой зафиксировано решение владельца

#### Scenario: Вердикт доменной сверки на стоп-знаке

- **WHEN** доменная сверка завершилась — применены канонические имена либо найдены новые понятия либо дубль предмета
- **THEN** стоп-знак называет вердикт сверки: применённые канонические имена, новые понятия с предложенными статьями глоссария, исход для дубля предмета; внесение статей в `GLOSSARY.md` — отдельное решение владельца вне операции

#### Scenario: Правка карточки возвращает к повторным прогонам

- **WHEN** владелец выбирает устранить находку
- **THEN** карточка правится, линтер и семантическая проверка прогоняются повторно, карточка возвращается на стоп-знак с новыми вердиктами

#### Scenario: Семантическая находка принята с обоснованием

- **WHEN** владелец принимает семантическую находку без правки
- **THEN** обоснование записывается в беклог, находка не блокирует принятие карточки
