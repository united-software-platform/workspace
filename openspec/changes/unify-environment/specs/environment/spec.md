# Spec Delta

## Purpose

Единый стандарт окружения зонтичного репозитория workspace: инструментарий поставляется через mise, сервисы — через локальный кластер k3s; стандарт делает подключение дочернего проекта механическим.

## ADDED Requirements

### Requirement: Инструментарий через mise

Окружение SHALL закреплять инструментарий в конфигурации `mise.toml`: рантайм проекта (`node`,
`python`) и CLI процесса разработки (`npm:@fission-ai/openspec`). Харнессы — claude, codex, dsh —
MUST NOT закрепляться в `mise.toml` и поставляться окружением: выбор харнесса остаётся
за пользователем.

#### Scenario: Свежий клон

- **WHEN** пользователь клонирует репозиторий и выполняет `mise install`
- **THEN** весь закреплённый инструментарий устанавливается локально без ручных шагов

#### Scenario: Харнесс вне поставки

- **WHEN** в окружение предлагают добавить claude, codex или dsh
- **THEN** `mise.toml` их не содержит: поставка не навязывает харнесс

### Requirement: Сервисы в k3s

Сервисы окружения SHALL исполняться в локальном кластере k3s: долгоживущие сервисы поставляются
манифестами helm в неймспейсах проектов-потребителей, одноразовые прогоны — Job'ами. Docker
Compose MUST NOT использоваться ни для сервисов, ни для одноразовых прогонов.

#### Scenario: Одноразовый прогон

- **WHEN** запускается одноразовый прогон окружения, например сканирование tldr
- **THEN** он исполняется Job'ом в кластере и завершается, не оставляя долгоживущих сервисов

#### Scenario: Дочерний проект подключает сервис

- **WHEN** дочернему проекту нужен сервис общего набора
- **THEN** сервис ставится helm-манифестом зонтика в неймспейс проекта-потребителя

### Requirement: Доступ к сервисам без публикации портов

Порты сервисов MUST NOT публиковаться на хост ни NodePort'ами, ни иным маппингом. Доступ
к сервису — `kubectl port-forward` на время обращения.

#### Scenario: Обращение к сервису

- **WHEN** пользователю нужен доступ к сервису кластера с хоста
- **THEN** он поднимает `kubectl port-forward` и обращается по локальному адресу; постоянной
  публикации порта не возникает

### Requirement: Переменные окружения в mise и .env

Несекретные значения окружения MAY объявляться в секции `[env]` файла `mise.toml`; умолчания
инструментов живут в самих инструментах, а не в `[env]` — значения `[env]` перекрывают
переменные process-окружения. Секреты SHALL лежать в git-ignored файле `.env`, подключаемом
mise; коммитимый шаблон `.env.example` MUST перечислять имена секретных переменных с пустыми
значениями. Значения в репозитории MUST NOT содержать секретов.

#### Scenario: Задача получает переменные

- **WHEN** задача mise запускается командой `mise run`
- **THEN** ей доступны значения `[env]` и `.env` без ручного экспорта

#### Scenario: Секрет не в git

- **WHEN** пользователь заполняет `.env` реальными значениями
- **THEN** `git status` не показывает `.env`, а `.env.example` содержит только имена с пустыми
  значениями

### Requirement: Задачи окружения в mise

Задачи окружения SHALL быть задачами mise и запускаться `mise run <имя>`: init-env, init-dirs,
init-gitignore, init-ssh-key, init-ssh-config, openspec-init, tldr-scan, tldr-scan-ext.
Задачи инициализации MUST быть идемпотентными и не перезаписывать существующие локальные
файлы. Makefile в репозитории MUST NOT использоваться.

#### Scenario: Инициализация свежего клона

- **WHEN** на свежем клоне выполняется `mise run init`
- **THEN** создаются `.env` из шаблона, каталоги `.ssh` и `.claude-accounts`, записи `.gitignore`
  и SSH-ключ проекта; повторный запуск ничего не перезаписывает

#### Scenario: Перечень задач

- **WHEN** пользователь выполняет `mise tasks`
- **THEN** задачи окружения перечислены с описаниями, без обращения к Makefile
