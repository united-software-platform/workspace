# Design

## Context

Три носителя правки: код утилиты (`tools/classifier/src/classifier/`), шаблон беклога
(`templates/classify.md`) и спека операции. Классификация живёт в
`application/classify.py`: порог проверяется на первенце уровня, причины копятся в `reasons`,
needs_confirmation — истина при непустом списке причин. Ранжирование — `domain/similarity.py`,
кандидаты уровня ранжируются косинусной близостью. Тесты — на фейковом клиенте embeddings
(`tests/fakes.py`), сетевых обращений нет. Каталоги прогонов classify лежат в `backlog/`
и занесены в `.gitignore` — файлы контрактов в каталоге прогона приватность не нарушают.

Приватность: в коммитимые артефакты change'а не попадают имена реальных проектов и адреса
прогонов; проверочные прогоны — на вымышленных карточках.

## Goals / Non-Goals

**Goals:**

- Прогон classify выполняется только по закоммиченному состоянию выгрузки таксономии.
- Малый отрыв primary от secondary отражается в контракте как потребовавший подтверждения.
- Вход и выход прогона фиксируются файлами в каталоге прогона.

**Non-Goals:**

- Калибровка самой шкалы близости (нормировка, температура) — отдельная тема; margin
  констатирует сжатие, не чинит его.
- Правка навыка-обёртки `.claude/skills/classify/SKILL.md` — проверка закоммиченности
  живёт в шаблоне, единственном исполнителе прогона (решение Q9 прожарки).
- Изменение стоп-знака принятия: владелец по-прежнему решает сам; правка только добавляет
  ему информацию.

## Decisions

### D1. Проверка закоммиченности — в предусловии 1.3 шаблона

`git status --porcelain tools/classifier/taxonomy/` — непустой вывод означает
незакоммиченные правки выгрузки: стоп с названным препятствием, беклог пригоден
к продолжению после коммита. Альтернатива — проверка в навыке-обёртке до порождения
беклога — отклонена: вторая копия правила; остановленный беклог сохраняет состояние
и продолжается после коммита без порождения нового.

### D2. Margin — константа домена, критерий в слое приложения

`MARGIN = 0.02` объявляется в `domain/similarity.py` рядом с ранжированием. Проверка
живёт в `application/classify.py` после ранжирования: отрыв = confidence(primary) −
confidence(second); отрыв < MARGIN → причина в `reasons`, needs_confirmation=true.
Значение 0.02 разнесло наблюдаемые случаи: ложные уровни прогона-примера имели отрывы
0.0052–0.0114 (попали бы под флаг), верный SUB-037 — 0.0715, верный DOM-003 — 0.0311.
Не CLI-флаг: преждевременная конфигурируемость без накопленной статистики прогонов.

### D3. Отрыв считается только при наличии второго кандидата

Уровень с единственным кандидатом не даёт отрыва: причин по margin не возникает.
Критерий порога для такого уровня действует как раньше. Это следует из механики
ранжирования (secondary нет — сравнивать не с кем) и фиксируется тестом.

### D4. Контракты — файлы в каталоге прогона, фронтматтер сохраняется

Задача 2.2 шаблона дополнительно пишет `card.json` и `classification.json` в каталог
прогона. Дублирование сознательное: файлы машиночитаемы и переживают временный каталог,
фронтматтер самодостаточен для чтения; каталог прогона в `.gitignore` — приватность
не нарушается. Норма оформлена по образцу действующего прогона с тремя носителями
контрактов.

### D5. Проверочные прогоны — на вымышленных карточках, критерии через exit code

Валидация margin: закупочная вымышленная карточка после WRSP-024 — ожидание
needs_confirmation=true (уровни L3/L4 с малыми отрывами) с причинами в `reasons`;
код возврата `1`. Регресс порога: карточка без purpose — needs_confirmation=true без
обращения к эндпоинту, код `1`, поведение без изменений. Юнит-тесты margin — на фейковом
клиенте без сети: отрыв выше/ниже 0.02, единственный кандидат уровня, порог отдельным
критерием.

## Risks / Trade-offs

- **Более частые стоп-знаки с подтверждением.** Прогоны с малыми отрывами теперь честно
  просят внимания владельца. Это назначение правила: ложная уверенность хуже лишнего
  вопроса.
- **Ветвление причин.** В `reasons` могут одновременно появиться порог и margin — список
  причин копится, rationale собирается из состава; контракт уже это допускает.
- **Счётчики загрузки в спеке.** Синхронизация счётчиков с выгрузкой — ручная; рассинхрон
  уже случился (L2 36→37, L3 25→27, L4 34→35), правка устраняет его в этом change'е
  и дальше счётчики в спеке привязаны к фактам выгрузки.
