# Design

## Context

Замеры эмбеддингами (тот же эндпоинт и модель, что у утилиты) показали два независимых источника отказов по отрыву: (а) записи-близнецы в справочниках совпадают на 0.85–0.91 — карточка совпадает с обеими почти поровну, отрыв физически ограничен; (б) объективно двойные проекты сидят между далёкими записями (0.761), обе гипотезы валидны. Требования — proposal.md; изменяемое поведение — три дельта-спеки. Ключевые числа: margin 0.02 (`domain/similarity.py:13`), условие needs_confirmation — `application/classify.py:144–149`, контракт — `docs/contracts.md`.

## Goals / Non-Goals

Goals:

- убрать отказы, рождённые самим справочником (близнецы), — склейкой записей;
- двойным проектам давать честную составную метку вместо отказа;
- адресация старых отчётов переживает склейку (алиасы).

Non-Goals:

- слияние различимых понятий (ERP/BPMS, разработка/тестирование) — только истинные синонимы;
- изменение margin или порога; веса уровней; заострение описаний неклеимых пар (отдельная работа);
- касание ручного цикла дополнения карточки (классификация остаётся детерминированной при фиксированном входе).

## Decisions

### D1. Граница склейки — семантическая тождественность, замер лишь кандидат-лист

Косинусная близость выдаёт кандидатов, решение принимает владелец по существу понятий. Порог кандидатов 0.85 отобрал шесть пар; из них шесть признаны тождествами, четыре родственные пары (0.88–0.90) оставлены раздельными. Канонический ID — более общее понятие пары (PRB-025 поглощает PRB-027: подготовка документов — частный случай ручной обработки; SUB-020 «Обработка данных» поглощает SUB-019 «Интеграция данных»). Альтернатива — клеить всё выше 0.88 — отвергнута: «Разработка ПО» и «Тестирование ПО» на 0.881, но слияние потеряет реальное различие.

### D2. Алиас — в записи, не отдельный справочник

Поле `aliases: [<ID>]` в канонической записи. Старые отчёты и записи проектов резолвятся поиском по ID и по алиасу; отдельный файл переименований не заводится — второй носитель соответствия разошёлся бы при первой же правке. Утилита в кандидаты выдаёт канонический ID; алиас — дело потребителя контракта.

### D3. A&B-метка — в выходном контракте, сборка в сцене применения

Условие отрыва (первый–второй кандидат < margin) убирается из needs_confirmation. Вместо отказа уровень с малым отрывом получает `combined_label`: склейка имён кандидатов в пределах margin (« & », до трёх). Код возврата `1` сужается до непройденного порога — сегодня он смешивает две несопоставимые ситуации. A&B-итог проходит как код `0`: обе гипотезы уже в результате, роль primary сохраняется (первенец по confidence), метка показывает связку. Авто-режим и ручной стоп-знак трактуют метку одинаково — принято/к принятию, без needs_confirmation.

### D4. Обратная совместимость контракта

`combined_label` — новое поле, старые потребители его игнорируют; `reasons` теряют вид причины по отрыву — потребительское поле, изменений схемы нет. `needs_confirmation` остаётся булевым: true только для пустого purpose и непройденного порога.

## Risks / Trade-offs

- [Тройственная метка редка, но возможна] → потолок три кандидата в метке; если в пределах margin оказались три — метка из трёх, это честно отражает пограничность.
- [Склейка меняет поведение классификатора на прежних карточках] → осознанно: часть прошлых needs_confirmation станет classified — ожидаемый эффект, проверяется перепрогоном пакета 20261116171306.
- [Алиас не виден в кандидатах утилиты] → потребитель резолвит по полю aliases записи; контракт документирует.
- [SUB-019 «Интеграция данных» исчезает как самостоятельный кандидат] → её семантика в объединённом описании SUB-020; карточки про интеграцию находят объединённую запись.

## Migration Plan

Правки справочников уменьшают счётчики — манифест обновляется той же правкой. Код утилиты и контракт меняются одномомременно с справочниками (иначе разъедется трактовка кода 1). Откат — возврат записей из git-истории справочников и revert утилиты; следов в данных нет (прогоны перечитывают таксономию при каждом запуске).
