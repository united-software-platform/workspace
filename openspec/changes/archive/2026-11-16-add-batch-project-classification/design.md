# Design

## Context

Сегодня классификация проекта — цепочка ручных операций: навык `classify` оборачивает беклог `classify`, а карточку для него владелец добывает отдельным прогоном `classify-project` с двумя стоп-знаками. Утилита `tools/classifier/` уже вызывается напрямую из беклога и возвращает коды `0` (порог пройден), `1` (`needs_confirmation=true`), `2` (ошибка входа или окружения). Мотивация пакетного прогона — proposal.md, раздел Why; требования — specs/batch-project-classification/spec.md.

## Goals / Non-Goals

Goals:

- один прогон навыка покрывает десятки проектов без участия владельца после принятия списка;
- решения исполнителя-автомата прослеживаются: авторство каждого выбора записано во фронтматтер беклога и отражено в сводном отчёте;
- ручные операции `classify` и `classify-project` остаются нетронутыми.

Non-Goals:

- точечный перезапуск упавших проектов — повтор новым прогоном либо одиночным навыком `classify`;
- вложенная автоматизация беклога `classify` — его спека объявляет «Режима авто нет», и изменение это объявление не пересматривает;
- изменение утилиты классификации и её контрактов.

## Decisions

### D1. Оркестратор — сам навык, агенты — через `Agent` с выбираемой моделью

Навык `classify-batch` спрашивает модель исполнителя при опросе списка: уровни haiku (умолчание), sonnet, opus, fable; конкретная модель уровня разрешается платформой через `ANTHROPIC_DEFAULT_<УРОВЕНЬ>_MODEL` — навык передаёт уровень, а не ID модели. После принятия списка навык порождает по одному фоновому агенту на проект инструментом `Agent` с `model: <выбранный уровень>` и `subagent_type` общего назначения. Агент получает имя проекта, порог, штамп пакета, свой номер и уровень исполнителя; его задача — породить и исполнить беклог `classify-project-auto` по своему проекту и вернуть структурный результат. Выбранный уровень передаётся в беклог значением `runner_model`, авторство решений во фронтматтере пишется именем уровня.

Альтернатива — жёсткая модель haiku без вопроса — отвергнута владельцем: управляемость важнее, стоимость регулируется выбором уровня. Альтернатива — последовательный прогон в одном сеансе — отвергнута прожаркой: на десятках проектов время прогона растёт линейно, а фоновые агенты идут параллельно.

### D2. Шаблон `classify-project-auto` — самостоятельная операция, а не режим флага

Заводится новый шаблон `templates/classify-project-auto.md`, а не признак `--flag auto` у существующего `classify-project.md`. Признак оставил бы в одном шаблоне два противоположных порядка (стоп-знаки есть/нет) и заставил бы каждый прогон читать оба варианта. Отдельный шаблон дублирует группу поиска и составления карточки, но каждая строка читается в одном режиме. Ручной шаблон не правится — его «Стоп-знак.» принадлежит владельцу.

### D3. Автопринятие развязано с кодами возврата утилиты

Беклог авто-операции вызывает утилиту напрямую и трактует коды возврата:

- `0` — чистый результат: исполнитель-автомат принимает классификацию, авторство `haiku` пишется во фронтматтер `confirmed.classification`;
- `1` — `needs_confirmation`: проект получает статус `failed` с причиной `needs_confirmation`, данные классификации сохраняются в записи (владельцу есть смотреть);
- `2` — ошибка входа или окружения: статус `failed` с причиной ошибки.

Автопринятие «всего подряд» отвергнуто прожаркой: поднимать `needs_confirmation` автоматом значило бы присваивать неуверенную классификацию без ведома владельца.

### D4. Точки решений — обычные задачи без маркеров «Стоп-знак.»

Норма BKL-007 требует подтверждения владельца перед необратимой задачей, а порядок `/backlog:backlog-run` не принимает заранее данное подтверждение. В авто-шаблоне выбор источника и принятие классификации оформлены обычными задачами с записью решения и авторства во фронтматтер — конфликт с нормой не возникает, потому что стоп-знака в шаблоне просто нет. Авто-прогон не необратим: он не создаёт задач, не пишет в трекер и не коммитит.

### D5. Итоговый JSON и карточки — внутри игнорируемого `projects/`

Оркестратор единственный пишет `projects/{YYYYMMDDHHMMSS}.json` по завершении всех агентов; агенты возвращают структурный результат, фрагментных файлов нет. Карточки пишут агенты в `projects/{штамп}.cards/item-NN.json` — они переживают прогон для разбора полётов, но не попадают в коммит. `projects/` и `/backlog/classify-project-auto/` добавляются в `.gitignore` в блок `domain-classifier` — рядом с уже игнорируемыми следами ручных операций.

### D6. Поиск — тот же провайдер, ослабленный кворум

Поиск источников идёт тем же провайдером perplexity (`WEBSEARCH_*`), но кворум ослаблен: продолжение при ≥1 результате вместо ровно 5, фактическое число фиксируется в записи. Ноль результатов — `failed` с причиной «поиск не дал результатов».

## Risks / Trade-offs

- [Haiku выбирает нерелевантный источник из слабых результатов] → выбор агента записывается во фронтматтер с авторством, сводный отчёт называет каждый выбор; владелец перепроверяет подозрительные записи и перезапускает их одиночным прогоном.
- [Список проектов принят с опечаткой] → опрос до полного принятия показывает итоговый состав перед запуском; исправление — до принятия бесплатно, после — новый прогон.
- [Параллельные агенты перегружают эндпоинт поиска] → искусственный лимит параллельности не вводится: платформа ограничивает фоновые агенты сама; при деградации провайдера проекты получают `failed` с причиной и не роняют прогон.
- [Дублирование групп задач между ручным и авто-шаблоном] → принятая цена за чистоту каждого шаблона (D2); при расхождении контрактов карточки источником остаётся `tools/classifier/docs/contracts.md`.

## Migration Plan

Изменение чисто добавляющее: новые файлы навыка и шаблона, две записи в `.gitignore`. Откат — удаление файлов и записей; данных и состояния не затрагивается. Развёртывание не требуется: навык и шаблон читаются из рабочего дерева.
