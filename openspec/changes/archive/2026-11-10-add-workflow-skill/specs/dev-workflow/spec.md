# Spec Delta

## Purpose

Запуск операции workflow от требования до прожарки: вход требования, построение предмета-адреса прогона, делегирование порождению и исполнению беклога, контракт шаблона операции.

## ADDED Requirements

### Requirement: Вход требования обёртки

Навык `/workflow` SHALL принимать требование владельца текстом вызова. Вызов без требования
MUST получать ровно один вопрос о требовании; получив ответ, обёртка продолжается без повторных
вопросов о недостающем вводе.

#### Scenario: Вызов с требованием

- **WHEN** владелец зовёт `/workflow` с текстом требования
- **THEN** обёртка не спрашивает требование и переходит к построению предмета

#### Scenario: Вызов без требования

- **WHEN** владелец зовёт `/workflow` без текста
- **THEN** обёртка задаёт один вопрос о требовании и продолжает после ответа

### Requirement: Предмет прогона — адрес, а не формулировка

Предметом беклога операции workflow SHALL быть строка `{YYYYMMDDHHMMSS}-{краткое_описание_на_анг}`:
штамп локального времени в момент вызова и слаг из 2–5 английских слов через дефис по смыслу
требования. Исходная формулировка владельца MUST NOT становиться предметом и именем каталога следа;
она попадает в беклог значением `requirement`.

#### Scenario: Предмет построен по требованию

- **WHEN** требование сформулировано, предмет не назван владельцем явно
- **THEN** обёртка строит предмет из штампа и слага и показывает его в составе собранного вызова

#### Scenario: Формулировка не адрес

- **WHEN** требование дано на русском языке
- **THEN** каталог следа несёт штамп с латинским слагом, а не исходную формулировку

### Requirement: Делегирование порождению

Обёртка SHALL делегировать порождение беклога навыку `/backlog:backlog-generate` с операцией
`workflow`, предметом-адресом и значениями `target` (репозиторий из `git remote get-url origin`)
и `requirement` (исходная формулировка). Собранный вызов `backlog generate` MUST показываться
владельцу целиком до прогона. Репозиторий обёртка MUST предлагать сама, а не спрашивать.

#### Scenario: Значения собраны обёрткой

- **WHEN** требование получено
- **THEN** вызов порождения несёт `target` из origin и `requirement` и показан целиком до прогона

#### Scenario: Шаблона нет

- **WHEN** в каталоге шаблонов нет `workflow.md`
- **THEN** обёртка передаёт отказ `backlog-generate` как есть и не заводит шаблон сама

### Requirement: Исполнение без повторного вопроса

После успешного порождения обёртка SHALL передавать исполнение `/backlog:backlog-run` без повторного
вопроса «исполнить либо остановиться»: вызов обёртки и есть заранее данный ответ «исполнить».
Стоп-знак перед необратимой задачей шаблона MUST сохраняться и спрашивать владельца всегда.

#### Scenario: Порождение завершено

- **WHEN** беклог порождён успешно
- **THEN** исполнение передаётся `/backlog:backlog-run` без вопроса об остановке

#### Scenario: Стоп-знак не снимается

- **WHEN** исполнение доходит до задачи со стоп-знаком
- **THEN** исполнитель спрашивает владельца перед необратимым шагом, как задано шаблоном

### Requirement: Контракт шаблона операции workflow

Шаблон `templates/workflow.md` версии 1.1.0 SHALL нести значение `requirement` во фронтматтере
порождённого беклога; задача выявления требования MUST читаться из `{{requirement}}`, а не из
`{{subject}}`. Вступительный текст шаблона MUST NOT называть `subject` исходной формулировкой
владельца: `subject` — адрес прогона. Правка шаблона MUST завершаться приёмкой
`backlog check-template` с кодом возврата `0`.

#### Scenario: Фронтматтер несёт требование

- **WHEN** беклог порождён по шаблону 1.1.0
- **THEN** фронтматтер содержит `requirement` с исходной формулировкой и `subject` с адресом прогона

#### Scenario: Приёмка шаблона

- **WHEN** шаблон поправлен до версии 1.1.0
- **THEN** `backlog check-template templates/workflow.md` возвращает `0`
