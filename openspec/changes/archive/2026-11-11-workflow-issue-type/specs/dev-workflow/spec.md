# Spec Delta: dev-workflow

## MODIFIED Requirements

### Requirement: Контракт шаблона операции workflow

Шаблон `templates/workflow.md` SHALL нести значение `requirement` во фронтматтере порождённого
беклога; задача выявления требования MUST читаться из значения `requirement` фронтматтера,
а не из `{{subject}}`. Вступительный текст шаблона MUST NOT называть `subject` исходной
формулировкой владельца: `subject` — адрес прогона. Правка шаблона MUST завершаться приёмкой
`backlog check-template` с кодом возврата `0`.

Шаблон операции workflow SHALL определять тип задачи перед её созданием на GitHub. Тип выбирается
из организационных шаблонов репозитория `united-software-platform/.github`, каталог
`.github/ISSUE_TEMPLATE` — источник истины; редактируемые копии шаблонов в проекте MUST NOT
создаваться. Организационные шаблоны исполнитель получает через локальный кеш
`~/.cache/wrsp/issue-templates/`.

Кеш SHALL хранить файлы организационных шаблонов как есть — включая `config.yml` — и JSON-метаданные:
репозиторий-источник, SHA последнего полученного состояния `main`, время получения в UTC, перечень
файлов. Кеш MUST лежать вне репозитория, не коммититься и не правиться вручную.

Работа с кешем SHALL идти по алгоритму:

- кеша нет — получить SHA `main`, загрузить каталог `.github/ISSUE_TEMPLATE`, проверить полноту
  (число файлов совпадает с перечнем каталога; каждый `*.md` несёт YAML-фронтматтер с `name`
  и `labels`) и сохранить кеш с метаданными;
- кеш есть — сначала получить текущий SHA `main`; при совпадении использовать кеш; при изменении —
  загрузить каталог заново, проверить, атомарно заменить кеш и обновить метаданные;
- GitHub недоступен — использовать последний доступный кеш и сообщить владельцу его SHA
  и время получения;
- кеша нет и GitHub недоступен — остановиться до создания задачи и назвать причину.

Группа 3 «Задача на GitHub» SHALL состоять из пяти задач:

1. определить тип задачи из организационных шаблонов; исполнитель определяет тип сам
   с обоснованием, владелец вправе поправить; `config.yml` типом задачи не считается;
2. составить черновик задачи по выбранному шаблону, заполнив все его разделы; сведения,
   которых не хватает, MUST выясняться у владельца до создания задачи — выдумывать содержимое
   и оставлять обязательные поля пустыми запрещено; раздел, для которого сведений действительно
   нет, закрывается явной пометкой «— (нет)» после вопроса владельцу; черновик записывается
   во фронтматтер значением `issue_draft`, выбранный тип — значением `issue_type`;
3. провести первую прожарку черновика через `/mattpocock-skills:grilling` — уточнять формулировки
   и границы, пока задача не заполнена по шаблону и готова к созданию;
4. стоп-знак: показать владельцу итоговый состав — тип, заголовок `task_ref`, заполненный шаблон;
   после подтверждения создать задачу командой `gh issue create --repo {{target}} --title
   "<task_ref>" --body-file <файл черновика> --label <labels из фронтматтера шаблона>`; флаг
   `--template` не используется;
5. сверить созданную задачу: заголовок совпадает с `task_ref`, тело повторяет черновик.

Задача 5.1 «Прожарка формирования изменений» SHALL передавать прожарке контекст задачи целиком:
тип (`issue_type`), черновик после первой прожарки (`issue_draft`), `issue_url` и `branch` —
дальнейшая прожарка начинается с конкретного черновика, а не с пустого описания.

#### Scenario: Фронтматтер несёт требование

- **WHEN** беклог порождён по шаблону операции workflow
- **THEN** фронтматтер содержит `requirement` с исходной формулировкой и `subject` с адресом прогона

#### Scenario: Приёмка шаблона

- **WHEN** шаблон операции workflow поправлен
- **THEN** `backlog check-template templates/workflow.md` возвращает `0`

#### Scenario: Тип определён по организационному шаблону

- **WHEN** требование выявлено и исполнитель выбирает тип задачи
- **THEN** тип назван с обоснованием из организационных шаблонов, владелец вправе его поправить

#### Scenario: Кеш отсутствует и получен впервые

- **WHEN** кеша `~/.cache/wrsp/issue-templates/` нет
- **THEN** получены SHA `main`, каталог шаблонов, проверена полнота и кеш сохранён с метаданными

#### Scenario: SHA совпал

- **WHEN** кеш существует и SHA `main` совпал с записанным
- **THEN** шаблоны взяты из кеша без загрузки

#### Scenario: SHA изменился

- **WHEN** кеш существует и SHA `main` отличается от записанного
- **THEN** каталог загружен заново, проверен, кеш заменён атомарно, метаданные обновлены

#### Scenario: GitHub недоступен, кеш есть

- **WHEN** получить SHA не удалось, а кеш существует
- **THEN** шаблоны взяты из кеша, владельцу названы его SHA и время получения

#### Scenario: GitHub недоступен, кеша нет

- **WHEN** получить шаблоны не удалось и кеша нет
- **THEN** операция остановлена до создания задачи с названной причиной

#### Scenario: Черновик заполнен по шаблону

- **WHEN** тип выбран и организационный шаблон прочитан
- **THEN** черновик несёт все разделы шаблона, недостающие сведения выяснены у владельца,
  пустых разделов нет; черновик и тип записаны во фронтматтере `issue_draft` и `issue_type`

#### Scenario: Первая прожарка проведена

- **WHEN** черновик составлен
- **THEN** прожарка `/mattpocock-skills:grilling` уточняла его до готовности к созданию

#### Scenario: Задача создана после подтверждения

- **WHEN** владелец подтвердил итоговый состав на стоп-знаке
- **THEN** задача создана с телом из файла черновика и ярлыком из фронтматтера организационного
  шаблона

#### Scenario: Черновик передан в шаг 5

- **WHEN** задача создана и исполнение дошло до группы 5
- **THEN** прожарка формирования изменений получила тип, черновик целиком, `issue_url` и `branch`
