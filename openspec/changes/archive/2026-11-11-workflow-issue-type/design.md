# Design

## Context

Шаблон операции `templates/workflow.md` (версия 1.2.0 в рабочем дереве) исполняется ядром плагина
backlog: порождение `backlog generate` подставляет значения и проверяет структуру беклога, исполнение
идёт по `/backlog:backlog-run`. Организационные шаблоны задач лежат в репозитории
`united-software-platform/.github`, каталог `.github/ISSUE_TEMPLATE`: 7 шаблонов задач
(`architecture`, `bug`, `feature`, `incident`, `spike`, `task`, `tech-debt`) и `config.yml`
(запрет blank issues). Каждый шаблон задач несёт YAML-фронтматтер с `name`, `about`, `labels`.
Доступ к GitHub — через `gh` (аутентификация и права проверяются задачей 1.3 группы «Предусловия»).
Мотивация — в proposal.md; требования — в дельте спеки.

## Goals / Non-Goals

**Goals:**

- явный тип задачи при создании на GitHub и заполнение описания по организационному шаблону
  как структуре итогового тела;
- воспроизводимый доступ к организационным шаблонам через кеш с контролем свежести по SHA;
- сохранение механизмов беклога: стоп-знак, фронтматтер значений, структурная проверка порождения;
- передача первично заполненной задачи в прожарку шага 5.

**Non-Goals:**

- правка обёртки `.claude/skills/workflow/SKILL.md` — она состава задач не несёт;
- правка ядра плагина backlog — подстановки и проверки используются как есть;
- редактируемые копии организационных шаблонов в проекте — источник истины один;
- автоматическое определение типа без обоснования и без права владельца поправить;
- миграция уже порождённых беклогов — правка действует только на следующие порождения.

## Decisions

1. **Правка только шаблона операции.** Состав задач, порядок и проверки живут в
   `templates/workflow.md`; обёртка и ядро остаются без изменений. Альтернатива — отдельный скрипт
   кеша в `tools/` — отвергнута: шаги операции исполняются агентом, и скрипт дал бы второй носитель
   того же алгоритма, расходящийся при первой правке.

2. **Кеш в `~/.cache/wrsp/issue-templates/`, не в дереве проекта.** Кеш — свойство окружения
   агента: дерево проекта не засоряется, риск коммита исключён физически, требование «не коммить
   вместе с навыком» выполняется само. Альтернатива — каталог в проекте под `.gitignore` — отвергнута:
   игнорирование держится на дисциплине, а не на расположении. Метаданные — JSON рядом с файлами
   шаблонов: репозиторий-источник, SHA `main`, время UTC, перечень файлов.

3. **Свежесть по SHA `main`, атомарная замена.** Сверка SHA перед каждым использованием: совпал —
   кеш пригоден; изменился — загрузка в новый каталог и переименование поверх старого (атомарная
   замена не оставляет полукаши). Альтернатива — сверка по времени жизни кеша — отвергнута: TTL
   угадывается, SHA проверяется.

4. **Создание задачи через `--body-file`, а не `--template`.** Тело черновика многострочно
   и несёт Markdown организационного шаблона; файл обходит экранирование shell. Ярлык типа берётся
   из фронтматтера выбранного шаблона (`--label`), флаг `--template` не используется: он потребовал
   бы, чтобы GitHub применил шаблон на стороне репозитория, а черновик уже заполнен и прожарен.

5. **Черновик во фронтматтере беклога (`issue_draft`, `issue_type`).** Значения исполнения несёт
   фронтматтер (BKL-005): сеанс порождения и сеанс исполнения могут не совпадать, и черновик
   в памяти агента беклог межсеансовой пригодности не даёт. Построчный парсер фронтматтера ядра
   многострочные значения терпит — подтверждено порождением с многострочным `requirement`.

6. **Пять задач группы 3 вместо трёх.** Стоп-знак сдвигается с 3.1 на 3.4 — за ним остаётся
   единственное необратимое действие (создание задачи), а выбор типа, черновик и первая прожарка
   идут до него как обратимые шаги. Единая последовательность «тип → черновик → прожарка →
   стоп-знак → создание» вместо двух отдельных остановок: дубль собеседования не давал бы ничего.

## Risks / Trade-offs

- [Каталог `~/.cache/wrsp/` отсутствует или недоступен] → задача кеша трактуется как «кеша нет»
  и идёт по ветке первого получения; ошибка записи останавливает задачу с названной причиной.
- [Организационный репозиторий изменил состав шаблонов между listing'ом и загрузкой] → проверка
  полноты идёт по перечню того же listing'а, который породил загрузку; расхождение — повторная
  проверка, при повторении — стоп с названной причиной.
- [Фронтматтер беклога растёт на черновик целиком] → черновик по шаблонам организационного
  репозитория — единицы килобайт; парсер ядра многострочность терпит. Рост следит задача 3.2,
  избыточного текста черновик не несёт — заполнен по разделам шаблона.
- [Тип определён неверно при самостоятельном выборе] → тип называется владельцу с обоснованием
  на задаче 3.1 и остаётся видимым на стоп-знаке 3.4 до необратимого шага; владелец правит
  до создания.

## Migration Plan

Правка поднимает версию шаблона выше 1.2.0 и принимается `backlog check-template` (код возврата `0`).
Действие на уже порождённые беклоги не распространяется: они допорабатываются по своему составу
задач. Откат — возврат прежней версии шаблона из системы контроля версий; порождённые после правки
беклоги откату не подлежат и остаются пригодными к исполнению в своём составе.

## Open Questions

Нет: решения зафиксированы прожаркой и подтверждены владельцем.
