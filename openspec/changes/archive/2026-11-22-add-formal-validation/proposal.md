# Proposal

## Why

Третий уровень проверки требований — формальный — был отложен до появления требований
с конфликтующими числовыми и состоятельными ограничениями (решение change
`add-multilevel-requirements-validation`). Владелец запросил его реализацию по факту первого
реального прогона `requirement-add` (BR-001): у уровней 0–1 осталась непокрытой проверка,
которую линтер и семантика не доказывают, — непротиворечивость множества критериев как
математического факта. Заодно владелец запросил поддержку английского входа: импортированные
требования и англоязычные стейкхолдеры. У публичного Kiro такого уровня нет (факт-чек:
EARS + LLM без решателей) — гейт строится свой.

## What Changes

- **Новая команда формальной проверки** `tools/reqlint/formal.py <карточка>`: селектор
  критериев (temporal / quant / unformalizable), детерминированная компиляция канонической
  формы в LTL и SMT, решатели SPOT и Z3 в контейнере формальной проверки, отчёт
  `{consistent + witness | contradiction + core | vacuous | skipped}` с обратным переводом
  формул на язык карточки. Образ собирается задачей mise из Dockerfile репозитория; после
  сборки прогон офлайн, детерминирован — повторный прогон даёт тот же результат.
- **Каноническая форма критерия** — единственный вход компилятора: `[условие] → [субъект]
  [предикат] [порог + единица]`. LLM между текстом и решателем запрещён; приведение
  свободного текста в канон — шаг вызова, утверждаемый владельцем до формализации.
- **Двуязычный вход RU/EN**: паттерны селектора и таблица правил компиляции двуязычные;
  отчёт — на русском, цитаты — в языке карточки.
- **Английские правила линтера** `tools/reqlint/rules-en.yml`: категории A–F в формате
  `{name, pattern, hint, error}` — уровень 0 получает английский вход тем же change'ом.
- Вне рамок: автоматический вызов из прогона `requirement-add` (стоп-знак не зависит
  от формальной проверки — вызов всегда явный); реализуемость (realizability, синтез
  стратегий) — доказывается только выполнимость; правка шаблона операции и спеки
  `requirement-add-operation`.

## Capabilities

### New Capabilities

- `formal-validation`: формальная проверка критериев бизнес-требований — селектор,
  детерминированный перевод в LTL/SMT через каноническую форму, решатели SPOT/Z3,
  отчёт с witness, unsat-core и vacuity, двуязычный вход RU/EN.

### Modified Capabilities

_Нет_: операция `requirement-add` не меняется — формальная проверка вызывается отдельно
и в её прогон не встраивается.

## Impact

- Новые файлы: `tools/reqlint/formal.py`, `tools/reqlint/rules-en.yml`. Ничего существующего
  не правится: `reqlint.py`, `rules.yml`, `templates/requirement-add.md` и спека
  `requirement-add-operation` остаются как есть.
- Зависимости: решатели исполняются в контейнере формальной проверки — образ
  `workspace-formal` на Debian trixie: `python3-spot` из официального apt-репозитория LRDE
  (страница установки Spot, канал GPG-подписан), `z3-solver` — пин из PyPI; собирается
  задачей mise `formal-image` из `tools/reqlint/Dockerfile`. SPOT не распространяется через
  PyPI и apt Ubuntu (факт-чек применения). После сборки образа прогоны офлайн; инструменты
  хоста не растут (ENV-001 сохранён), контейнерные прогоны — принятый паттерн окружения.
- Дымовой прогон — BR-001: ожидаемый результат `skipped + тривиальный sat` (критерии
  без общих переменных) — фиксируется как подтверждение селективности гейта.
