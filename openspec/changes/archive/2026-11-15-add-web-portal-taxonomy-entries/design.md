# Design

## Context

Выгрузка таксономии — девять JSON-файлов в `tools/classifier/taxonomy/`: `manifest.json`
со счётчиками записей по каждому файлу и файлы уровней с полями `schema_name`, `schema_version`,
`source`, `record_count`, `records`. Записи уровней — `id` (`DOM-/SUB-/PRB-/SOL-NNN`), `code`,
`name`/`name_ru`, `description`/`description_ru`. Манифест несёт notes, среди которых: выгрузка
не содержит реальных проектов и организаций; термины e-commerce в выгрузке — универсальные записи
таксономии. Классификатор читает выгрузку целиком, включая `record_count` файлов; записи уровней
векторизуются, и добавление записей расширяет пространство сопоставления без правки кода.
См. proposal.md — Why.

## Goals / Non-Goals

**Goals:**
- Дополнить L4 архетипом «Информационный веб-портал» (`SOL-034`) и L2 поддоменом «Публикация
  официальной информации» (`SUB-036`) — записями в стиле существующих: id, code (kebab-case
  по английскому имени), name/name_ru, description/description_ru.
- Синхронизировать `record_count` в файлах уровней и в `manifest.json` с фактическим составом.
- Сохранить работоспособность утилиты: прогон classify по карточке завершается кодом `0`,
  новые записи участвуют в сопоставлении.

**Non-Goals:**
- Правка кода классификатора, контрактов и README (README правится только если фиксирует
  численность уровней — проверяется задачей).
- Пересмотр зафиксированных классификаций прошлых прогонов и беклогов classify.
- Пересмотр правил классификации (`classification_rules.json`), структуры уровней
  (`structure.json`) и остальных файлов выгрузки.
- Правка L1/L3: уровни покрывают кейс (L1 стабильно даёт «Государственный сектор»).

## Decisions

**D1. Записи без правки правил и кода.** Выгрузка — данные для векторизации; новые записи
подхватываются утилитой автоматически. Альтернатива — правка правил сопоставления
(`classification_rules.json`) отклонена: дефект — отсутствие записи, а не правило.

**D2. Формулировки записей — общие, не отраслевые.** Архетип назван «Информационный
веб-портал» (information-web-portal), поддомен «Публикация официальной информации»
(official-information-publishing): формулировки описывают класс систем (публичная публикация
для неограниченной аудитории), а не конкретную отрасль, поэтому архетип применим и к корпоративным
порталам, и к медиа. Альтернатива — узкое «Government Portal» — отклонена: таксономия
универсальная, и отраслевое имя сузило бы применимость записи без выигрыша в точности
(L1 уже покрывает отрасль).

**D3. Тексты записей — по паре английский/русский с согласованным code.** Каждая запись несёт
`code` (kebab-case от английского имени), `name`/`name_ru`, `description`/`description_ru` —
как у соседних записей уровня. Описания — одно-два предложения, в стиле соседних записей:
описание несёт суть класса, не примеры отраслей.

**D4. Синхронизация счётчиков — ручная правка двух файлов уровней и манифеста.** `record_count`
в файле уровня и в соответствующей строке `files` манифеста увеличивается на единицу. Альтернатива —
скрипт пересчёта — отклонена: правка разовая, скрипт оставил бы в репозитории мёртвый код.

**D5. Верификация прогоном и юнит-проверками выгрузки.** Подтверждение — прогон classify
по контрольной карточке портального класса: код `0`, новый архетип в кандидатах L4, новый поддомен
в кандидатах L2. Дополнительно — валидация JSON и уникальности идентификаторов простыми проверками,
без новых зависимостей.

## Risks / Trade-offs

- [Запись L4 не поднимется в primary по контрольной карточке — косинусная близость ниже соседей]
  → Контрольный прогон обязателен задачей; при непопадании в primary — дополнение описания записи
  (description обогащается признаками класса: новости, документы, события, публикация) и повторный
  прогон; порог принятия — primary L4 у нового архетипа или первое место среди secondary
  с отношением к primary, при котором primary не спорный класс (CRM/BPM/инженерные системы).
- [Смещение secondary-кандидатов у прочих классов проектов] → Приемлемо по proposal: боковое
  изменение пространства сопоставления; зафиксированные классификации не пересматриваются.
- [Рассинхрон record_count, если править только файлы уровней] → Задача правит и манифест;
  юнит-проверка сверяет счётчики с фактическим числом записей.
- [Векторизация новой записи хуже соседей из-за нетипичных формулировок] → Формулировки D3
  выдержаны в стиле соседних записей (те же поля, длина, стиль описаний); контрольный прогон
  покажет отклонение.

## Migration Plan

Правка данных выгрузки, обратимая git-откатом файлов. Порядок: дополнить L2 и L4 → синхронизировать
манифест → прогон классификации по контрольной карточке → юнит-проверки выгрузки. Откат —
восстановление файлов из git. Развёртывания и пересборки нет: выгрузка читается утилитой
при каждом прогоне.

## Open Questions

Нет: номер свободного идентификатора, стиль записей и состав правки зафиксированы проверкой
выгрузки; остальное закрывается контрольным прогоном.
