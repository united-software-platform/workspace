# Spec Delta

## ADDED Requirements

### Requirement: Навык карточного прогона
Репозиторий SHALL содержать навык `classify-batch` — пакетный прогон классификации по готовым карточкам без веб-поиска и обогащения. Вход — JSON-массив карточек по входному контракту утилиты классификации: путь к файлу вне репозитория либо массив текстом вызова. Модель исполнителя и порог принимаются вызовом с умолчаниями `haiku` и `0.5`. Прогон исполняют фоновые агенты по одному на карточку.

#### Scenario: Массив текстом вызова
- **WHEN** владелец вызывает навык с JSON-массивом карточек в тексте вызова
- **THEN** навык принимает массив как состав пакета и не переспрашивает его

#### Scenario: Массив путём файла
- **WHEN** владелец называет путь к JSON-файлу массива карточек вне репозитория
- **THEN** навык читает массив из файла и принимает его как состав пакета

#### Scenario: Умолчания модели и порога
- **WHEN** вызов не назвал модель исполнителя и порог
- **THEN** прогон идёт на уровне `haiku` с порогом `0.5`, авторство решений записывается как `haiku`

#### Scenario: Карточки не коммитятся
- **WHEN** карточный прогон завершён
- **THEN** карточки хранятся только в игнорируемом git каталоге `projects/` и не коммитятся

### Requirement: Шаблон операции classify-card-auto
Репозиторий SHALL содержать шаблон операции `classify-card-auto`: беклог элемента без стоп-знаков и без цикла дополнения — карточка берётся готовой, утилита классификации вызывается напрямую один раз. Решения исполнителя-автомата и их авторство SHALL записываться во фронтматтер беклога.

#### Scenario: Порождение беклога карточной операции
- **WHEN** фоновый агент исполняет операцию `classify-card-auto` для карточки пакета
- **THEN** порождается беклог без маркеров «Стоп-знак.», карточка адресуется значением операции

#### Scenario: Один вызов утилиты
- **WHEN** беклог карточной операции доходит до классификации
- **THEN** утилита вызывается один раз с готовой карточкой и порогом; повторные вызовы и дополнение карточки не выполняются

#### Scenario: Чистый результат принят
- **WHEN** утилита вернула код `0`
- **THEN** исполнитель-автомат принимает классификацию, включая метки «A & B» из `combined_labels`; элемент получает статус `classified`

#### Scenario: Код 1 — отказ без дополнения
- **WHEN** утилита вернула код `1` (`needs_confirmation`)
- **THEN** элемент получает статус `failed` с причиной `needs_confirmation`, данные классификации сохраняются в записи прогона

#### Scenario: Код 2 — ошибка входа или окружения
- **WHEN** утилита вернула код `2`
- **THEN** элемент завершается отказом с причиной ошибки, повторные вызовы не идут

### Requirement: Окружение карточного прогона
Карточный прогон SHALL проверять перед запуском агентов только переменные `EMBEDDINGS_BASE_URL`, `EMBEDDINGS_API_KEY`, `EMBEDDINGS_MODEL` и закоммиченную выгрузку таксономии; переменные веб-поиска карточному прогону не требуются.

#### Scenario: Запуск без переменных веб-поиска
- **WHEN** окружение не задаёт переменные `WEBSEARCH_*`, а владелец запустил карточный прогон
- **THEN** прогон идёт до конца, отсутствие переменных веб-поиска препятствием не считается

#### Scenario: Переменных embeddings нет
- **WHEN** окружение не задаёт переменные `EMBEDDINGS_*`
- **THEN** прогон останавливается до запуска агентов, препятствие названо владельцу

### Requirement: Запись карточного прогона
Итоговый файл карточного прогона SHALL следовать контракту записи прогона: `project_name` берётся из карточки, `source` = `null` — источник не выбирается, `card` несёт карточку из входного массива, `classification` — итог утилиты либо `null`, `status` и `failure_reason` — по исходу элемента.

#### Scenario: Запись успешного элемента
- **WHEN** оркестратор пишет запись классифицированной карточки
- **THEN** запись содержит имя из карточки, статус `classified`, `source` = `null`, карточку и итог утилиты

#### Scenario: Запись упавшего элемента
- **WHEN** элемент завершился с кодом `1`
- **THEN** запись содержит статус `failed`, причину `needs_confirmation` и данные последней классификации

## MODIFIED Requirements

### Requirement: Навык enrich-прогона
Репозиторий SHALL содержать навык `classify-batch-enrich`, принимающий вызов без значений, опрашивающий владельца и формирующий список проектов до полного принятия итогового состава; после принятия навык запускает классификацию всех проектов списка с обогащением через веб-поиск.

#### Scenario: Опрос до принятия списка
- **WHEN** владелец вызывает навык `classify-batch-enrich` и называет проекты
- **THEN** навык показывает итоговый состав списка и продолжает опрос до явного принятия владельцем

#### Scenario: Запуск классификации после принятия
- **WHEN** владелец принял список проектов
- **THEN** навык запускает классификацию каждого проекта списка фоновыми агентами на выбранной модели исполнителя

### Requirement: Цикл дополнения в авто-режиме
При коде возврата `1` (`needs_confirmation`) беклог операции `classify-project-auto` SHALL исполнять цикл дополнения: анализ `reasons`, дополнение карточки данными выбранного источника и повторный вызов утилиты, до трёх попыток в одном беклоге. Беклог операции `classify-card-auto` цикла дополнения не содержит.

#### Scenario: Дополнение развело кандидатов
- **WHEN** первый вызов утилиты вернул код `1`, а после дополнения карточки повторный вызов вернул код `0`
- **THEN** классификация принимается исполнителем-автоматом, попытка дополнения фиксируется во фронтматтере

#### Scenario: Три попытки не помогли
- **WHEN** все три вызова утилиты вернули код `1`
- **THEN** элемент получает статус `failed` с причиной `needs_confirmation`, запись прогона несёт данные последней классификации

#### Scenario: Карточка перезаписывается на месте
- **WHEN** исполнитель-автомат дополняет карточку по спорным уровням из `reasons`
- **THEN** карточка перезаписывается по пути `projects/{штамп}.cards/item-NN.json`, счётчик и ход дополнений фиксируются во фронтматтере беклога

#### Scenario: Ошибка окружения не дополняется
- **WHEN** утилита вернула код `2`
- **THEN** элемент завершается отказом с причиной ошибки, цикл дополнения не запускается

### Requirement: Сводный отчёт по выборам
По завершении прогона владелец SHALL получать сводный отчёт по автоматическим выборам на точках решений: принятые классификации по каждому проекту; enrich-прогон дополнительно называет выбранные источники. Упавшие элементы перечисляются с причинами.

#### Scenario: Отчёт после прогона
- **WHEN** оркестратор enrich-прогона завершил все проекты и написал итоговый файл
- **THEN** владелец получает сводный отчёт по выборам источников и принятым классификациям

#### Scenario: Отчёт после карточного прогона
- **WHEN** оркестратор карточного прогона завершил все карточки и написал итоговый файл
- **THEN** владелец получает сводный отчёт по принятым классификациям, упавшие элементы — с причинами
