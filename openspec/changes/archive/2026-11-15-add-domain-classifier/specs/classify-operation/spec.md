# Spec Delta

## Purpose

Операция беклога `classify`: прогон классификации проекта по шагам со стоп-знаком
принятия результата владельцем и циклом дополнения данных карточки до состояния
готовности, без автоматического присвоения классификации.

## ADDED Requirements

### Requirement: Шаблон операции classify
Репозиторий SHALL содержать шаблон операции беклога `classify` в `templates/classify.md`,
порождение беклога командой `backlog generate --operation classify` и исполнение
навыком `/backlog:backlog-run` по общему порядку исполнения беклогов.

#### Scenario: Порождение беклога
- **WHEN** выполняется `backlog generate --operation classify` с предметом
  и значениями
- **THEN** беклог порождается по шаблону и проходит `backlog lint`

#### Scenario: Исполнение беклога
- **WHEN** беклог операции classify исполняется навыком `/backlog:backlog-run`
- **THEN** задачи идут по порядку с признаком «выполнено ранее» и стоп-знаком
  перед принятием результата

### Requirement: Значения операции classify
Операция classify SHALL принимать значения: `card` — путь к файлу карточки проекта
вне репозитория, `threshold` — порог confidence (опционально, по умолчанию 0.5).
Карточка в репозиторий не попадает; прогон не коммитится и попадает в игнор, если
решает владелец.

#### Scenario: Значения переданы
- **WHEN** беклог порождён со значениями `card` и `threshold`
- **THEN** беклог несёт значения во фронтматтере, вызов утилиты использует их

#### Scenario: Карточка вне репозитория
- **WHEN** операция завершена
- **THEN** файл карточки и его копии в репозитории отсутствуют

### Requirement: Шаг вызова утилиты
Беклог classify SHALL содержать задачу вызова утилиты классификации с карточкой
из значения `card` и порогом из значения `threshold`; результат (JSON-контракт)
показывается владельцу.

#### Scenario: Утилита вернула контракт
- **WHEN** утилита завершилась с кодом `0` или `1`
- **THEN** контракт классификации показан владельцу до принятия

#### Scenario: Утилита завершилась с ошибкой
- **WHEN** утилита завершилась с кодом `2`
- **THEN** ошибка названа владельцу, исполнение останавливается до её устранения

### Requirement: Стоп-знак принятия
Беклог classify SHALL останавливаться на стоп-знаке после показа результата:
владелец принимает классификацию либо отказывает. Подтверждение фиксируется
во фронтматтере беклога. Режима авто нет: без явного принятия классификация
не считается присвоенной.

#### Scenario: Принятие
- **WHEN** владелец подтвердил результат на стоп-знаке
- **THEN** подтверждение записано во фронтматтер, операция завершается

#### Scenario: Отказ
- **WHEN** владелец отказал
- **THEN** исполнение прекращается, беклог остаётся пригодным к продолжению;
  следующий прогон — новый беклог с дополненной карточкой

### Requirement: Цикл дополнения данных
Операция classify SHALL поддерживать цикл: отказ на стоп-знаке — дополнение данных
карточки владельцем — новый беклог с новой карточкой — новый прогон, до состояния
готовности. Дополненная карточка — новый файл вне репозитория.

#### Scenario: Повторный прогон
- **WHEN** после отказа владелец дополнил карточку и породил новый беклог
- **THEN** новый прогон использует дополненную карточку, прежний беклог не правится

### Requirement: Навык-обёртка classify
Репозиторий SHALL содержать навык-обёртку `classify` (по образцу навыка `workflow`),
принимающий путь к карточке одним вызовом и делегирующий порождение и исполнение
беклога операции classify.

#### Scenario: Вызов обёртки
- **WHEN** владелец вызывает навык classify с путём к карточке
- **THEN** обёртка строит предмет прогона, предлагает target и порождает беклог
  операции classify без повторных вопросов
