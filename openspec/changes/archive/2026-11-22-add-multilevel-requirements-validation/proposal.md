# Proposal

## Why

Проверка требования в операции `requirement-add` — один уровень: строчный линтер `reqlint` (задача 2.4
шаблона) ловит дефекты лексически — неоднозначные слова, слабые модальности, отсутствие единиц.
Но три из четырёх классов дефектов требований по природе не видны построчному линтеру:
противоречие живёт **между** строками (критерии друг с другом, Description с Success Criteria),
неполнота — в пробелах между полями, «рецепт реализации» — в лексически безобидных
формулировках, диктующих решение. Ссылка на модель Kiro (EARS + семантический LLM-проход
по критериям с рубрикой классов дефектов) показывает стандартный состав второго уровня —
семантическая проверка карточки целиком. Операция только создана (WRSP-032, принята карточка
BR-001): встраивать второй уровень нужно сейчас, пока модель прогона не застыла и карточек мало.

## What Changes

- **Уровень 0 расширен** — `tools/reqlint/rules.yml` получает правила недостающих классов:
  категория «F: рецепт реализации» (лексические маркеры решения в формулировке требования)
  и правило измеримости критерия (критерий-строка без числа и порога). `reqlint.py` не меняется —
  правила декларативные, схема `{name, pattern, hint, error}` уже поддерживается.
- **Уровень 1 добавлен** — семантическая проверка карточки целиком: новая задача шаблона
  операции после линтера. Исполнитель проверяет карточку по рубрике четырёх классов дефектов —
  неполнота, двусмысленность, противоречие, рецепт реализации, — включая кросс-проверки между
  полями и между критериями внутри Success Criteria. Выход — находки фиксированного вида
  `{класс, цитата, уточняющий вопрос}`.
- **Стоп-знак сводит оба уровня** — задача 3.1 шаблона называет вердикты линтера и семантической
  проверки: находки severity `error` и семантические находки любого класса — каждая с решением
  владельца (устранить правкой и повторить прогоны либо принять с обоснованием).
- Вне рамок: формальный гейт (перевод критериев в LTL/SMT и доказательство непротиворечивости
  решателем) — отдельное будущее изменение, оправданное появлением требований с конфликтующими
  числовыми и состоятельными ограничениями; повторная проверка уже зафиксированных артефактов
  `docs/requirements/`; EARS-синтаксис для критериев не вводится — измеримость несут правила
  линтера.

## Capabilities

### New Capabilities

_Нет_: новая способность не вводится — проверка требования остаётся поведением операции
`formular`.

### Modified Capabilities

- `requirement-add-operation`: добавляются требования двухуровневой проверки карточки —
  правила четырёх классов дефектов в линтере, семантическая проверка карточки целиком
  и сведение вердиктов двух уровней на стоп-знаке. Capability переименована из
  `formular-operation` change'ом `rename-formular-skill-to-requirement-add`; эта дельта несёт
  только `ADDED`-требования с новыми именами, не пересекающимися с её требованиями,
  и применяется после переименования.

## Impact

- Правятся файлы: `tools/reqlint/rules.yml` (новые правила), `templates/requirement-add.md`
  (новая задача в группе прожарки, расширение стоп-знака, версия шаблона 1.3.0).
  `reqlint.py` 0.2.0 и навыки-обёртки (`.claude/skills/requirement-add/`,
  `.zcode/skills/requirement-add/`) не правятся: обёртка не перечисляет задачи шаблона.
- Зависимости: новых инструментов нет — семантическую проверку исполняет сам исполнитель
  беклога по рубрике, записанной в шаблоне; отдельный вызов модели и внешние сервисы
  не привлекаются.
- Порядок: change применяется после `rename-formular-skill-to-requirement-add` — дельта
  адресует переименованную capability. Существующий артефакт BR-001 не перерабатывается:
  новые правила действуют на будущие прогоны.
