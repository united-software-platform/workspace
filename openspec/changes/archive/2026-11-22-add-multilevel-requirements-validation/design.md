# Design

## Context

Операция `requirement-add` (переименована из `formular` change'ом
`rename-formular-skill-to-requirement-add`) уже несёт уровень 0: задача 2.4 шаблона
прогоняет `tools/reqlint/reqlint.py --config tools/reqlint/rules.yml` по строке на поле карточки.
Линтер — строчный: правило видит одну строку, классификация находок — severity `error`/`warn`,
категории правил кодируются префиксами имён (A–E в `rules.yml`). Шаблон операции —
`templates/requirement-add.md` версии 1.2.0. Мотивация второго уровня — в `proposal.md` (Why).

## Goals / Non-Goals

**Goals:**

- Закрыть лексически доступные пробелы уровня 0: рецепт реализации и измеримость критерия.
- Дать карточке семантическую проверку целиком — по рубрике четырёх классов дефектов —
  силами исполнителя беклога, без новых инструментов и внешних вызовов.
- Свести вердикты двух уровней на стоп-знаке в единый список решений владельца.

**Non-Goals:**

- Формальный гейт (LTL/SMT, доказательство непротиворечивости решателем) — вне этого изменения.
- EARS-синтаксис для критериев, повторная проверка зафиксированных артефактов
  `docs/requirements/`, реестр требований — вне объёма.
- Независимый ревьюер семантической проверки: проверяет тот же исполнитель, что прожаривал.

## Decisions

### D1. Уровень 0 — только декларативные правила, `reqlint.py` не трогается

Новые правила — записи схемы `{name, pattern, hint, error}` в `rules.yml`: категория
«F: рецепт реализации» (два правила: F1 — глаголы решения «реализовать через / использовать /
создать <сущность инфраструктуры>», F2 — явные технологии из короткого списка) и D3 —
измеримость (строка о критерии/проверке без числа, порога, чек-листа). Категория кодируется
префиксом имени по сложившейся конвенции A–E.

*Альтернатива:* расширять `reqlint.py` (поле `class`, новая severity) — отклонено: меняет код
ради косметики отчёта и ломает вызов, зафиксированный в шаблоне.

### D2. F-правила — `warn`, не `error`

Лексический маркер решения шумит на легитимных упоминаниях технологий (Source, Rationale,
обоснование «почему сейчас»). Блокирующая находка по шумному признаку вынуждает владельца
оправдываться на пустом месте. Финальное суждение о рецепте реализации несёт семантический
уровень — он видит роль упоминания в карточке.

### D3. Семантическая проверка — задача шаблона, рубрика в тексте задачи

Новая задача 2.5 после линтера: исполнитель проверяет карточку целиком по рубрике четырёх
классов (неполнота, двусмысленность, противоречие, рецепт реализации), включая отношения
Description ↔ Business Outcome ↔ Success Criteria и критериев между собой. Рубрика записана
в задаче шаблона — шаблон самодостаточен и версионируется вместе с задачами (1.2.0 → 1.3.0).

*Альтернатива:* отдельный файл рубрики (`tools/reqlint/rubric.md`) — отклонена: рубрика нужна
одной операции, вынос в файл появится, когда её потребует вторая точка вызова.

*Альтернатива:* скрипт с вызовом внешней LLM — отклонена: исполнитель беклога уже LLM;
внешний API — новая зависимость и ключ ради того, что делает сам исполнитель.

### D4. Находка несёт уточняющий вопрос

Формат находки `{класс, цитата, уточняющий вопрос}`: без вопроса находка вырождается
в придирку, с вопросом — превращается в прожарку на стоп-знаке. Классы фиксированы
перечислением, свободной классификации нет.

### D5. Стоп-знак сводит оба уровня, повторный прогон — оба уровня

Задача 3.1 называет вердикты линтера (2.4) и семантики (2.5); решение «устранить» возвращает
карточку к правке и повторению обоих прогонов — уровни не расходятся в вердиктах.

### D6. EARS не вводится

EARS-шаблоны («When … the system shall …») рассчитаны на системные требования; для
русскоязычной бизнес-карточки из девяти полей они ломают живой язык владельца. Измеримость
критериев несут правила B2, D2 и новое D3.

## Risks / Trade-offs

- [F-правила шумят на легитимных упоминаниях технологий] → severity `warn` (D2), роль
  упоминания оценивает семантический уровень и владелец.
- [Семантическую проверку делает тот же исполнитель, что прожаривал, — свои пробелы он может
  не заметить] → фиксированная рубрика, обязательные цитата и вопрос, повторный прогон после
  правки; независимый ревьюер — признанное ограничение (Non-Goal).
- [Рубрика в шаблоне растит его объём] → рубрика компактна, один класс — одна строка
  признаков; при росте — вынос в файл (D3, альтернатива).
- [Дельта адресует capability, переименованную change'ом
  `rename-formular-skill-to-requirement-add`] → только `ADDED`-требования с новыми именами;
  применяется строго после переименования.

## Migration Plan

Правила и шаблон обратно совместимы: существующие беклоги не перегенерируются, BR-001
не перерабатывается — новые правила действуют на будущие прогоны. Откат — возврат `rules.yml`
и `templates/requirement-add.md` к предыдущим версиям, лежащих в истории git.
