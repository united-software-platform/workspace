# Spec Delta

## ADDED Requirements

### Requirement: Каноническое единство имён уровней

Документы выгрузки таксономии (`structure.json`, `classification_rules.json`) SHALL именовать каждый уровень классификации одним каноническим русским именем. Для L3 каноническое имя — «Область проблем»; `classification_rules.json` MUST использовать его в разделе уровней.

#### Scenario: Имя L3 совпадает в документах выгрузки

- **WHEN** читаются определения уровня L3 в `structure.json` и `classification_rules.json`
- **THEN** русское имя уровня в обоих документах — «Область проблем»

### Requirement: Контракт данных объявляет алиасы

Контракт данных выгрузки (`data_model.json`) MUST объявлять необязательное поле `aliases` для сущностей всех четырёх уровней. Документ структуры (`structure.json`) MUST определять семантику алиаса: поглощённый идентификатор объединённой записи, разрешаемый к канонической записи уровня.

#### Scenario: Строгая валидация по контракту пропускает записи с алиасами

- **WHEN** записи уровней (SUB-009, SUB-020, PRB-003, PRB-011, SOL-010) проверяются по списку полей контракта данных
- **THEN** поле `aliases` не считается посторонним, записи проходят проверку

#### Scenario: Семантика алиаса описана в структуре

- **WHEN** читается `structure.json`
- **THEN** документ называет поле `aliases` и правило его разрешения: алиас указывает на каноническую запись, поглотившую выведенный идентификатор

### Requirement: Канонические идентификаторы в примерах

Записи `example_project.json` MUST ссылаться только на канонические идентификаторы записей уровней: идентификатор из `aliases` в присваивании примера запрещён.

#### Scenario: Ссылка примера разрешается без учёта алиасов

- **WHEN** потребитель читает присваивание SUB уровня примера «Pinecone Goods»
- **THEN** идентификатор — SUB-020 (канонический), и он разрешается записью уровня без механизма алиасов

### Requirement: Приоритет отрасли над сквозной функцией на L1

Правила классификации (`classification_rules.json`) MUST фиксировать правило выбора primary для L1: когда карточка проекта попадает и в отраслевую запись, и в сквозную функциональную запись (DOM-017 «Аналитика и отчётность»), отраслевая запись занимает primary, сквозная функциональная — secondary.

#### Scenario: Аналитическая система в отрасли

- **WHEN** классифицируется карточка проекта с отраслевой принадлежностью и аналитической функцией — например, BI-дашборд затрат медицинской организации
- **THEN** primary L1 — отраслевая запись (DOM-005), DOM-017 занимает secondary

### Requirement: Симметрия двуязычных описаний

Для каждой записи уровней английское и русское описания MUST выражать одно определение понятия: перечень существенных признаков совпадает, различается только язык.

#### Scenario: Описания SOL-035 совпадают по составу признаков

- **WHEN** читаются английское и русское описания записи SOL-035 «Государственная АИС»
- **THEN** оба описания называют регламентированную отчётность с электронной подписью, ведение реестров и аналитику использования поддержки

### Requirement: Согласованность кода и имени записи

Код (`code`) записи уровня MUST соответствовать полному имени записи: код, покрывающий только часть имени, приводится к полному соответствию. Для DOM-003 «Commerce & Trade» код — `commerce-and-trade`.

#### Scenario: Код DOM-003 отражает имя

- **WHEN** читается запись DOM-003
- **THEN** код записи — `commerce-and-trade`, имя — «Commerce & Trade»
