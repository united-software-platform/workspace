# Design

## Context

Выгрузка таксономии SPCF — девять JSON-файлов в `tools/classifier/taxonomy/`, загружаемых классификатором доменов и проверяемых тестами. Часть файлов писалась разными поколениями правок (видно по двум порядкам полей записей), контракт данных (`data_model.json`) отстал от фактического состава записей. Классификатор читает выгрузку по идентификаторам записей; манифест и счётчики consumers сверяют с `record_count`. Полное описание дефектов — в proposal.md (Why) и задаче WRSP-027 (issue #19).

## Goals / Non-Goals

**Goals:**

- Сделать выгрузку строго валидируемой по собственному контракту данных.
- Устранить терминологические конфликты документов выгрузки (имя L3, семантика алиасов).
- Зафиксировать правило выбора primary для сквозных записей L1.

**Non-Goals:**

- Изменение состава записей уровней, их канонических идентификаторов и счётчиков манифеста.
- Изменение алгоритма классификации и поведения прогонов.
- Введение машинной проверки терминов (симметрия описаний, каноничность имён) — контроль остаётся чтением и ревью.

## Decisions

### D1. Каноническое имя L3 — «Область проблем»

Источник понятия — `structure.json`: он вводит уровни классификации, `classification_rules.json` — потребитель. Меняем потребителя, не источник. Альтернатива («Область проблемы», правка structure.json) отвергнута: `structure.json` — точка определения терминов по правилам терминологии проекта, смена имени в источнике — большая правка, чем синхронизация потребителя.

### D2. `aliases` объявляется для всех четырёх сущностей уровней

Поле необязательное (записей без алиасов большинство), но объявлено в `fields` каждой сущности уровня в `data_model.json`. Альтернатива — отдельная сущность «алиасы» или вынос в файл соответствия — отвергнута: механизм уже физически живёт в записях уровней, отдельная сущность дублировала бы его и требовала бы миграции пяти существующих записей. Семантика фиксируется в `structure.json` в разделе `core_classification` — рядом с определением уровней, к которым алиасы относятся.

### D3. Разрешение алиасов — обязанность потребителя, источник хранит канонические ссылки

Пример «Pinecone Goods» исправляется на `SUB-020`. Альтернатива — сохранить `SUB-019` как демонстрацию разрешения алиасов — отвергнута: назначение `example_project.json` — демонстрация корректных присваиваний для обучения и сверки; неявная демонстрация механизма разрешения в данных смешивает обучающий пример с тестом потребителя. Если демонстрация разрешения алиасов понадобится — она станет сценарием спеки или тестом, а не данными.

### D4. Правило приоритета отрасль > сквозная функция

Правило добавляется текстом в `classification_rules.json` (запись в `records` о выборе primary при конфликте природы записей L1). Оно не кодируется в данных: определение «сквозная» — свойство семантики записи, а не отдельное поле; заводить булево поле `cross_cutting` ради одного DOM-017 — избыточно. Альтернатива — пометка в самой записи DOM-017 — отвергнута по той же причине.

### D5. Порядок полей выравнивается к формату нового поколения

Канонический порядок: `id`, `code`, `aliases` (при наличии), `name`, `name_ru`, `description`, `description_ru`. JSON порядок полей не контрактен, но единый порядок снижает шум диффов при будущих правках. Правка чисто текстовая — читатели JSON не затронуты.

## Risks / Trade-offs

- [Смена code DOM-003 `commerce` → `commerce-and-trade` может сломать потребителей, адресующих записи по code] → Проверка грепом по репозиторию: найдено только `taxonomy/` (см. tasks); если код используется вне репозитория, откат правки одного поля.
- [Правило D4 текстовое, без машинной проверки] → Сценарий спеки фиксирует ожидание; контроль — ревью прогонов классификации с аналитическими карточками.
- [Переупорядочивание полей L2/L4 создаёт большой дифф] → Дифф семантически пуст (JSON), файлы переписываются целиком, счётчики и id не меняются.

## Migration Plan

Изменения только в JSON-файлах данных, без миграций. Откат — revert коммита; состав записей не меняется, совместимость потребителей сохраняется.
