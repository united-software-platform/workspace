# Spec Delta

## ADDED Requirements

### Requirement: Контекст глоссария в прогоне

Беклог requirement-add SHALL содержать предусловие обязательного чтения `GLOSSARY.md` —
единственного источника канонических понятий домена — и добавления его в контекст прогона
до выявления требования. Понятие формулировки вне глоссария — кандидат в новые понятия
доменной сверки.

#### Scenario: Глоссарий в контексте до прожарки

- **WHEN** беклог requirement-add начинает группу прожарки
- **THEN** `GLOSSARY.md` прочитан целиком и находится в контексте исполнителя: канонические имена и Avoid-имена понятий домена известны

#### Scenario: Глоссария нет — прогон не начинается

- **WHEN** файл `GLOSSARY.md` в корне репозитория отсутствует
- **THEN** исполнение останавливается до выявления требования, владельцу называется препятствие

### Requirement: Доменная сверка предмета и терминов

Беклог requirement-add SHALL содержать задачу доменной сверки между выявлением требования
и прожаркой: предмет по смыслу сверяется с существующими BR из `docs/requirements/`, термины
формулировки — с `GLOSSARY.md`. При введении новых понятий исполнитель SHALL вызвать навык
`/mattpocock-skills:domain-modeling` и согласовать их с текущим доменом. Вердикт сверки
MUST называться на стоп-знаке принятия.

#### Scenario: Новый предмет

- **WHEN** сверка не нашла предмет в `docs/requirements/`, термины согласованы с доменом
- **THEN** прогон продолжает формирование нового BR, вердикт сверки — «новый предмет»

#### Scenario: Термин получает каноническое имя

- **WHEN** формулировка использует понятие, уже определённое в `GLOSSARY.md` под другим именем
- **THEN** поля карточки заполняются каноническим именем понятия из глоссария

#### Scenario: Дубль предмета

- **WHEN** предмет требования по смыслу совпадает с существующим BR из `docs/requirements/`
- **THEN** новый BR не заводится — прогон ведёт правку существующего BR новой версией по правилам документации, ID требования не меняется

#### Scenario: Новые понятия согласованы с доменом

- **WHEN** формулировка вводит понятия, отсутствующие в `GLOSSARY.md`
- **THEN** вызван навык `/mattpocock-skills:domain-modeling`, понятия согласованы с предметами, сущностями, доменными службами и атрибутами текущего домена по классификации глоссария, предложенные статьи глоссария названы на стоп-знаке

## MODIFIED Requirements

### Requirement: Стоп-знак сводит вердикты трёх уровней

Стоп-знак принятия SHALL называть вердикты трёх уровней: находки линтера severity `error`,
семантические находки любого класса и вердикт доменной сверки. Каждая названная находка
MUST получить решение владельца: устранить правкой карточки с повторением прогонов либо
принять с обоснованием, записанным в беклог. Без решения по каждой названной находке
и по вердикту сверки принятие не происходит.

#### Scenario: Оба вердикта на стоп-знаке

- **WHEN** владельцу показывают карточку на стоп-знаке
- **THEN** названы находки линтера severity `error` и семантические находки всех классов, по каждой зафиксировано решение владельца

#### Scenario: Вердикт доменной сверки на стоп-знаке

- **WHEN** доменная сверка завершилась — применены канонические имена либо найдены новые понятия либо дубль предмета
- **THEN** стоп-знак называет вердикт сверки: применённые канонические имена, новые понятия с предложенными статьями глоссария, исход для дубля предмета; внесение статей в `GLOSSARY.md` — отдельное решение владельца вне операции

#### Scenario: Правка карточки возвращает к повторным прогонам

- **WHEN** владелец выбирает устранить находку
- **THEN** карточка правится, линтер и семантическая проверка прогоняются повторно, карточка возвращается на стоп-знак с новыми вердиктами

#### Scenario: Семантическая находка принята с обоснованием

- **WHEN** владелец принимает семантическую находку без правки
- **THEN** обоснование записывается в беклог, находка не блокирует принятие карточки
