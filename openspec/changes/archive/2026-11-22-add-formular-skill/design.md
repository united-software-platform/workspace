# Design

## Context

В репозитории стоят две операции с навыками-обёртками: `workflow` (`templates/workflow.md`,
навык `workflow-grill` — от требования до задачи на GitHub и ветки, с прожаркой) и
`workflow-fast` (`templates/workflow-fast.md` — то же без прожарки), плюс `classify`-семейство.
Обёртки принимают ввод одним вызовом, строят предмет `{YYYYMMDDHHMMSS}-{slug}`, делегируют
`/backlog:backlog-generate` и передают исполнение `/backlog:backlog-run`; грамматика шаблонов
принимается ядром `backlog check-template`. Мотивация — в `proposal.md` (issue #27, WRSP-032).

Навыки живут в двух точках входа с одинаковым содержанием: `.claude/skills/<имя>/SKILL.md`
и `.zcode/skills/<имя>/SKILL.md` (сверено `diff` по workflow-fast и workflow-grill).

Допущения, принятые без ответов владельца на уточняющий раунд (вопросы заданы, ответов не было):
имена `formular`/`formular`. Допущение «карточка остаётся в беклоге» владелец отменил 2026-11-21
после первого прогона: беклог обязан порождать артефакт в `docs/requirements/` — карточка
во фронтматтере недоступна для дальнейшей работы с требованием.

## Goals / Non-Goals

**Goals:**

- Шаблон операции `formular`, порождающий беклог прожарки BR по девяти полям; принятая карточка
  фиксируется артефактом `docs/requirements/<ID>.md`.
- Навык-обёртка `formular` в двух точках входа — от требования до требования-документа одним
  вызовом.

**Non-Goals:**

- Единый реестр-индекс требований (сводный файл со списком карточек): занятость номеров
  и перечень несут имена файлов `docs/requirements/`; индекс появится, когда накопится.
- Назначение статусов `Approved` и `Deprecated`: это решения о приёме требования в работу,
  а не о его формировании.
- Создание задач на GitHub, веток и коммитов — их несут операции `workflow`.

## Decisions

1. **Имена: операция `formular`, навык `formular`.** Слово из формулировки владельца («беклог
   formular»), симметрия «имя навыка = имя операции» как у workflow-fast, беклоги лягут
   в `backlog/formular/`. Альтернатива `requirement-formation` отвергнута: длиннее и ломает
   симметрию с уже стоящими обёртками.

2. **Структура шаблона — грамматика workflow-fast.md.** Фронтматтер с подстановками
   `template_version`, `date`, `operation`, `subject`, `runner`, `requirement` (+ парные
   `*_scalar` для порождения), значения `br_card: null` и `confirmed.irreversible_step: null`;
   группы задач с «Проверка» и «Выполнено ранее» у каждой. Отличия от workflow-fast:
   нет значения `target` и группы «Задача на GitHub» — операция с GitHub не работает;
   вместо них группа прожарки и стоп-знак принятия. Состав групп:

   - 1 Предусловия: прочитать `/backlog:backlog-run`, прогнать `backlog lint`. Проверки GitHub
     нет — операция его не касается.
   - 2 Прожарка BR: выявить требование из `requirement` (что/зачем/какая задача); провести
     прожарку `/mattpocock-skills:grilling` по девяти полям — уточнять, пока каждое поле
     не заполнено, недостающее спрашивать у владельца, выдумывать запрещено; собрать карточку
     и записать в `br_card` со статусом `Draft`.
   - 3 Стоп-знак принятия: показать карточку по девяти полям; принятие — Status `Proposed`,
     отказ — `Rejected` с причиной; вердикт и подтверждение фиксируются во фронтматтере;
     при отказе исполнение останавливается, карточка остаётся свидетельством.
   - 4 Фиксация: принятая карточка записывается артефактом `docs/requirements/<ID>.md`
     по правилам DOC-014 и DOC-022; отклонённая карточка файл не получает.
   - 5 Итог: назвать карточку, путь артефакта и путь беклога.

3. **Два носителя карточки: рабочее значение и артефакт.** Во время прогона карточка живёт
   во фронтматтере значением `br_card` (YAML с ключами `id`, `name`, `description`,
   `rationale`, `business_outcome`, `success_criteria`, `priority`, `status`, `source`) —
   это обеспечивает самодостаточность прогона (BKL-005) и читается проверками беклога.
   После принятия на стоп-знаке карточка фиксируется артефактом `docs/requirements/<ID>.md`:
   имя файла — ID карточки (уникальность номера следует из уникальности имён файлов), файл
   строится по правилам документации репозитория — DOC-014 (заголовок, назначение,
   навигация) и DOC-022 (таблица версий), несёт все девять полей. Артефакт — продукт операции;
   беклог остаётся свидетельством прогона. Отклонённая карточка артефакта не получает.
   Альтернативы отвергнуты: карточка только в беклоге — недоступна для дальнейшей работы
   (отменено владельцем); единый реестр-файл — сводный индекс до накопления карточек избыточен.

4. **Статусная модель на стоп-знаке.** Карточка рождается `Draft`; принятие владельцем —
   `Proposed` (сформировано и согласовано, годится как вход для workflow/openspec); отказ —
   `Rejected`. `Approved`/`Deprecated` операция не назначает (см. Non-Goals). Альтернатива
   «принятие = Approved» отвергнута: Approved — приём в работу, отдельное решение владельца.

5. **ID `BR-NNN`.** Номер предлагает исполнитель по занятым номерам — файлам каталога
   `docs/requirements/`, подтверждает владелец — паттерн GIT-010 (подбор «по смыслу» без
   подтверждения запрещён).

6. **Навык-обёртка — структура SKILL.md навыка workflow-fast**, разделы «Вход», «Порядок»,
   «Передача исполнения», «Отказы», «Версионирование». Порядок короче на шаг `target`:
   вызвать `/backlog:backlog-generate` с операцией `formular`, предметом и одним значением
   `requirement`; собранный вызов показывается владельцу до прогона. Файл кладётся одинаковым
   в `.claude/skills/formular/` и `.zcode/skills/formular/`, версия 1.0.0 со ссылкой WRSP-032.

7. **Линтинг формулировок — шаг шаблона между сборкой карточки и стоп-знаком.** Инструмент —
   `tools/reqlint/reqlint.py` (форк Wyzer-it/reqlint 0.1.0 → 0.2.0: поддержка `--config`
   с правилами `{name, pattern, hint, error}`, severity `error`/`warn`, показ совпадения)
   и `tools/reqlint/rules.yml` — правила владельца (категории A–E субъекта/scope/понятий/
   уровней/критериев). Цель прогона — значения полей карточки, по строке на поле: заголовок,
   навигация и таблица версий артефакта линтеру не подаются — на них правила дают шум
   (например, «Proposed» ловилось паттерном «PR»). Политика: находки `error` не запрещают
   принятие, но обязаны быть названы на стоп-знаке с решением владельца по каждой —
   устранить правкой либо принять с обоснованием в беклоге. При переносе правил починены
   два дефекта: E1 — границы слова (`\bPR\b`, раньше ложно ловил «Proposed», «принята»);
   D1 — вставка «прошлых» больше не разрывает паттерн малой выборки.

## Risks / Trade-offs

- [Шаблон не проходит приёмку ядра] → грамматика срисована с `templates/workflow-fast.md` 1:1,
  приёмка `backlog check-template` стоит задачей в tasks.md до любых прогонов.
- [Копии навыка в `.claude` и `.zcode` расходятся при правках] → как у стоящих навыков:
  правка вносится в оба файла одной задачей; сверка `diff` — в задачах и в спеке (сценарий
  «Навыки двух точек входа не расходятся»).
- [Расхождение карточки в беклоге и артефакта после правок] → артефакт рождается из `br_card`
  один раз на фиксации; дальнейшая жизнь требования (статусы, правки полей) идёт в артефакте,
  беклог — неизменное свидетельство прогона.
- [Каталог docs/requirements/ разрастается без индекса] → до накопления карточек индекс
  избыточен; перечень дают имена файлов, индекс заведётся отдельным изменением.
- [Прожарка соскальзывает в проектирование решения] → девять полей держат фокус на ЧТО/ЗАЧЕМ;
  критерии качества BR (ISO 29148) — обязанность прожарки, не карточки.
