# Design

## Context

В репозитории уже есть способность `code-scan`: скрипт `tools/tldr/scan.sh` снимает слепок стороннего
проекта в `reports/<имя>/` (18 JSON-отчётов; утилита живёт в Docker-образе). Слепок — срез текущего
состояния без авторства; история git — россыпь коммитов. Формат связывает одно с другим: договорённость
о том, как выгрузка работы человека из git ложится на код слепка. Отчёты слепка дают относительные
POSIX-пути с непоследовательными префиксами (`./`, `/project/`, без префикса); ревизия, на которой
снят слепок, нигде не зафиксирована. См. proposal.md — Why.

Ограничение приватности: данные проект-источника (имена, email, пути, отпечатки) не должны попасть
в коммитимые артефакты. Рамка изменения — только формат: инструмент извлечения — отдельное будущее
изменение (см. Non-Goals).

## Goals / Non-Goals

**Goals:**

- Описать машиночитаемый контракт «реализованная работа разработчика»: структура шапки и записей,
  типология работы, пара со слепком, границы области.
- Определить формат реестра идентичностей и выборку person/team.
- Описать детерминированную JSON-проекцию для Elastic/реляционной загрузки.
- Зафиксировать границы приватности: коммитимые документы — только вымышленные примеры.

**Non-Goals:**

- Инструмент извлечения выгрузки (CLI, Makefile-цель, верификация прогона) — отдельное будущее
  изменение.
- ES-mapping и реляционная DDL — потребитель контракта делает сам.
- Аналитика и сводные счётчики (KPI, «сколько отревьюил») — запросы потребителя поверх контракта.
- Извлечение ревью из git: в истории нет следа ревью, контракт несёт только механические факты.
- Группировка коммитов в «логические изменения» по коду задачи: коды и имена веток — плавающий
  источник истины, производный слой потребителя.

## Decisions

### D1. Канонический носитель — YAML, JSON — производная проекция

YAML — человекочитаемый канон, JSON — машинная проекция той же схемы (YAML⊃JSON). Одна структура
данных сериализуется дважды: `yaml.safe_dump(..., sort_keys=True, allow_unicode=True)` и
`json.dumps(..., ensure_ascii=False, sort_keys=True)`. Детерминированность даёт сортировка ключей
и стабильный порядок списков (коммиты — по дате, затем sha; пути — лексикографически).

Альтернатива — JSON как канон: отвергнута при обсуждении с пользователем: YAML выбран каноническим
носителем, JSON — проекцией.

### D2. Каноническая схема контракта (переносима в JSON без потерь)

```yaml
header:
  format_version: "1.0"
  generated_at: "<ISO-дата формирования>"
  registry: "<путь реестра>"
  selection: { kind: person | team, value: <slug | имя> }
  persons: [ { slug: …, name: …, emails: [ … ], team: … } ]   # вошедшие в выборку
  period: { from: …, to: … }        # отсутствует — вся история линии
  line: <имя ветки линии истории>
  snapshot: { name: <имя слепка>, taken_at: <дата съёмки слепка> }
  snapshot_revision_unknown: true    # оговорка: ревизия слепка не зафиксирована
  scope: { include: [ <префиксы и файлы> ], outside_count: <число путей вне области> }
commits:
  - sha: …
    authored_at: <ISO 8601 с датой и временем>
    author: <slug лица>            # кому принадлежит коммит (атрибутция в team-выборке)
    author_email: <email коммита>  # фактический email автора коммита из истории
    kind: code | integration
    merged: own | others          # только для integration
    subject: …
    body: …                       # отсутствует, если тела нет
    task: <код задачи>            # опциональная аннотация, best effort
    branch: <имя ветки>           # опциональная аннотация, best effort
    paths:
      - path: <POSIX-путь>
        status: A | M | D | R
        added: <int | null>       # null для binary
        deleted: <int | null>
        snapshot: found | missing  # пара со слепком
        symbols: [ { name: …, kind: …, line_start: …, line_end: … } ]  # опционально, для found
```

### D2a. Формат дат и порядок записей

Даты — ISO 8601 с датой и временем и смещением (`2026-04-14T11:28:12+03:00`). Коммиты
упорядочиваются по `authored_at` по возрастанию, при равенстве — по `sha`. Пути в статус-листе —
лексикографически. Для переименований (`R100`) статус `R`; пара со слепком строится по пути после
переименования.

Альтернатива порядку «сначала новые» — отвергнута: восходящий порядок дат даёт хронологию, читаемую
человеком, и стабильный дифф двух выгрузок.

### D2b. Пример в спецификации

Полный пример вымышленной выгрузки — шапка, запись `kind: code` с парой «найден + символы», запись
`kind: integration` с `merged: others`, запись с парой «в слепке не найдено» — приводится в
`docs/work-format.md`; значения вымышлены, структура нормативна.

### D3. Реестр идентичностей и группировка авторств

Реестр: `{ slug, name, emails: [], team }`. В выборку попадают коммиты с точным совпадением
`email автора ∈ emails` записи лица. Без нормализации адресов (trim, lower, «починка» опечаток):
реестр — источник истины, решение о слиянии адресов принимает ведущий реестра, код не догадывается.
Merge-коммиты входят в выборку автора merge как `kind: integration`; `merged: own | others`
определяется по коммитам второй родительской ветки: все принадлежат самому автору — `own`, есть
чужие — `others`.

Альтернатива — нормализация email кодом: отвергнута, тихие правки чужих адресов — риск ложных
склеек авторств.

Запись коммита несёт `author` (slug лица) и `author_email` (фактический адрес из истории): в
team-выборке записи нескольких лиц лежат одним списком, и группировка «коммиты по человеку» опирается
на эти поля.

### D3a. Граница выборки: линия и период

Выборка строится по одной линии истории (именованное поле `line` шапки) — история основной ветки
разработки; обход всех веток не выполняется, чтобы одни и те же изменения не попадали в выгрузку
дважды из feature-веток и merge-дублей. Период `period.from/to` — фильтр по `authored_at`,
отсутствует — вся история. Email коммиттера не учитывается: работа — авторство.

### D3b. Область и счётчик вне области

`scope.include` — список префиксов каталогов и/или имён файлов; путь входит в область, если начинается
с одного из префиксов или совпадает с одним из файлов. Конкретный состав области задаёт потребитель
формата при формировании выгрузки; в `paths` записей попадают только пути области, остальные
суммируются в `header.scope.outside_count` (уникальные пути за всю выборку). Это удерживает записи
коммитов сфокусированными на коде и отделяет шум сторонних артефактов.

### D3c. Ядро связки и аннотации

Множество существующих путей слепка — из `01-tree.json` (рекурсивный обход `children`): дешёвый
и полный источник существования пути. Символы для найденных путей — из `03-structure.json`
(классы и методы с диапазонами строк). Прочие отчёты слепка — опциональные аннотации по нужде
потребителя. Сопоставление символов — по имени, не по номерам строк: строки дрейфуют между коммитом
и слепком.

### D4. Таблица нормализации путей слепка (нормативная)

| Отчёт слепка | Ведущий префикс | Действие нормализации |
|---|---|---|
| `01-tree.json` (`path`), `03-structure.json` (`files[].path`) | — | нет, путь уже канонический |
| `04-health`, `10-secure`, `11-vuln`, `12-api-check`, `22-cognitive`, `24-clones`, `25-debt`, `32-inheritance` | `./` | отрезать ведущий `./` |
| `23-smells.json` | `/project/` | отрезать ведущий `/project/` |
| `20-hotspots`, `21-churn`, `30-calls`, `31-hubs`, `33-coupling`, `34-dead` | — | нет, путь уже канонический |

Для `30-calls` узлы графа `"path:symbol"` — путь до первого `:`; для `24-clones` — `fragment1.file`,
`fragment2.file`; для `32-inheritance` — `child_file`, `parent_file`.

### D5. Документация формата — `docs/work-format.md`

Спецификация формата: назначение, шапка (D2), схема записи (D2, D2a), таблица нормализации путей
(D4), границы области (D3b), JSON-проекция (D1), примеры типовых запросов потребителя (сколько влил
своих/чужих, +/- строк, коммиты по человеку) и вымышленный пример (D2b). Шаблон реестра
`docs/people.yaml` — вымышленные записи.

### D6. Гарантии приватности

Коммитимые документы (спецификация, шаблон реестра) несут только вымышленные значения: имена людей,
email, пути и слепка, и git — вымышленные; отпечатки проект-источника (объём истории, доли merge,
числа удалённых путей) не упоминаются. Реальные выгрузки и реальный реестр — локальные файлы вне git;
в сопроводительных документах изменения проект-источник обозначается нейтрально («смонтированный
репозиторий», «слепок»).

## Risks / Trade-offs

- [Слепок без ревизии] → семантика пары «присутствует в слепке» + оговорка `snapshot_revision_unknown`
  в шапке; потребитель не может утверждать «этот код родился этим коммитом».
- [Коды задач покрывают не всю историю] → код/ветка — опциональные аннотации best effort; группировка
  в «изменения» — производный слой потребителя.
- [Опечатки в email авторов] → реестр ведётся вручную, ведущий сам решает, вносить ли адрес-опечатку
  отдельной строкой; формат не нормализует и не чинит адреса.
- [Переименования после съёмки слепка] → пара строится по пути после переименования; возможны ложные
  `missing` для старых путей — оговорено в шапке.
- [Удалённые до слепка пути] → `missing` — ожидаемый массовый случай, не ошибка: запись коммита
  остаётся полной, аннотации слепка отсутствуют.
- [Разрастание выгрузки на длинной истории] → потребитель выбирает person/team/период; формат не
  пытается уместить историю всех людей в один документ.

## Migration Plan

1. Написать `docs/work-format.md` и шаблон `docs/people.yaml`.
2. Самопроверка: пример валиден как YAML, соответствует схеме D2, не содержит данных проект-источника.
3. Коммит документов.

Откат: удалить `docs/work-format.md`, `docs/people.yaml` — формат новый, зависимых систем нет.

## Open Questions

- Co-Authored-By: включать ли соавторов в выборку лица — можно решить при реализации инструмента
  извлечения, на структуру формата не влияет.
- Аннотации слепка сверх ядра (агрегаты истории, метрики качества): подключать ли как опциональные
  расширения — влияют только на опциональные поля пары, структура формата не меняется.
